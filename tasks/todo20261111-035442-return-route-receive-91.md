## Threat model (L-031) — read before implementing B and C

- **Who registers a session.** Only the AspNetCore endpoints (`InboundAdmission`, C1) after a successful unpack AND admission: the envelope was encrypted with an authcrypt layer (`UnpackResult.Encrypted && Authenticated`), its sender kid resolved to a DID subject (FR-CONSIST-01/05/06 already proved the key is authorized by that DID), it is not a `forward`, it carries `return_route: all`, and FR-RR-08 admitted it. `IReturnRouteSessionRegistry.Register` is public, so in-process host code can register its own `IReturnRouteSession`; that code is trusted (it already holds the facade and the secrets). Nothing about the seam is reachable by a remote peer except through the admission path above.
- **What a session can see / send.** A session exposes identity facts (`PeerDid`, `LocalDid`, `Mode`, `Thread`, `Transport`, `IsLive`, `Closed`) and ONE operation, `TrySendAsync(Message)`. It never exposes the socket, raw bytes, or the inbound. Every message sent through it is snapshotted (serialize → deserialize, so a handler retaining the instance cannot race the check), validated by the shared FR-RR-03 rule (`to` == exactly `[PeerDid]` and `from` == `LocalDid`, compared as DID subjects, L-034) and authcrypted from `LocalDid` to `PeerDid` by `DidCommClient.PackEncryptedAsync`. A handler holding another peer's session (via `Find`) can only push messages addressed to, and encrypted for, that peer.
- **Trust boundary = authcrypt, not the socket.** `PeerDid` is derived from the envelope's verified `skid` (never from plaintext `from`, never from the connection). A socket is a delivery hint. If a socket is hijacked, or if Mallory replays Alice's captured envelope from her own socket: (1) the replay guard refuses the duplicate, so no session opens; (2) even if a session existed, everything pushed on it is encrypted to Alice's keyAgreement keys — the socket holder receives ciphertext it cannot open. Confidentiality therefore survives a hijacked socket; what an attacker can do with a hijacked socket is drop or delay pushes (availability), which is the pre-existing transport trust level.
- **Observables, by design.** 200-vs-202 (and its timing) is visible only to the authenticated sender (FR-RR-04). Eviction is visible to the evicted peer (a normal close) — FR-RR-03 requires it. A replay drop is a 202 like an admitted message, so it is not a new oracle for unauthenticated parties (they cannot enter the scope).
- **Mutability / isolation.** `TrySendAsync` snapshots the message before validation and packing (as `TrySendReplyOnSocketAsync` does today). Registry events (`SessionOpened` / `SessionClosed`) are fire-and-forget; a throwing subscriber is caught, logged by type name, and cannot affect admission, dispatch or the response. Pushes are queued to a bounded per-socket channel; a full queue returns `false`, never blocks the handler, never grows memory beyond `MaxPendingPushes` packed messages per socket.
- **Audit.** Every drop / refusal / eviction logs the message id and an enum/type name only — never a DID, kid, thread id or message text (JC-6). `SessionOpened` / `SessionClosed` give #94 the lifecycle it needs without exposing the socket.
- **Adversarial line items** (F15): Mallory-with-`all` cannot read Bob's traffic; replayed Alice message on Mallory's socket opens nothing; oversized `return_route_thread`; HTTP response-body smuggling (two pushes → one body); fresh-DID flood against both bounded stores; log scan for DID/kid/thread values with the real `CapturingLoggerProvider`.

  3. Timestamped: `created < nowS - windowS` → `TooOld`; `created > nowS + skewS` → `FutureDated`; `expiresAt = created + windowS + skewS`. Missing: `RequireCreatedTime` → `MissingCreatedTime`; else `expiresAt = nowS + windowS` (retained `Window`, FR-RR-08 (2)).
  4. Under the lock: purge — `while (_expiry.TryPeek(out var key, out var exp) && exp < nowS)` dequeue and remove from its bucket (drop empty buckets); this is the ONLY removal path, so heap and buckets never diverge, each entry is popped once (amortized O(log n) per insert, serialized by the lock — no stampede, L-025). Then: bucket exists and contains id → `Duplicate` (no insert, no refresh). Else if `_count >= MaxEntries`, or (bucket exists and `bucket.Count >= MaxEntriesPerPeer`) → `Saturated` (increment `SaturationCount`; nothing evicted — unexpired entries are never evicted to make room). Else insert into bucket (create the bucket if absent — bucket count is bounded by `_count <= MaxEntries`), enqueue `(peer,id)` with `expiresAt`, `_count++` → `Admitted`.
  Retention property to document and test: an entry is present until `created + Window + skew` inclusive (strict `<` on purge) and age rejection starts at `created < now − Window`, so there is no instant at which a captured request is neither cached nor too old (FR-RR-08 (4)). Memory: keys are the peer subject (≤ 2048 by `DidSubjectOf`) and the id (≤ `MaxMessageIdLength`).
  Logging: `Saturated` and `MessageIdTooLong` are flood-shaped → first occurrence and every 1000th at Warning (the `ForwardHandler.DropLogEvery` pattern, one counter each), with counts only; other outcomes are not logged by the guard (the endpoint logs the drop with the id, C1).

## J. Judgment calls

- JC-1..JC-14 — as decided by the orchestrator (session API packs a plaintext `Message`; admission in AspNetCore, not the dispatcher; headerless same-socket replies end; `return_route_thread` cap; two options classes; id/type-name-only logs; no `OwnIdentifiers` gate; FR-RR-06 in scope; WS session semantics; registry bounds/concurrency; replay guard rules; public surface/compat; acknowledgement contract; `forward` never opens a session and is replay-exempt). All baked into A–F above.
- JC-15 — **No static class named `ReturnRoute`.** L-014: it would shadow the `DidComm.Transports.ReturnRoute` namespace for every importer. Constants and `TryRead`/`Read` live on `ReturnRouteHeader`. The pure eligibility and addressing rules live in Core as internal statics (`ReturnRouteEligibility`, `ReturnRouteAddressing`) so #92/#95 reuse them; the pipeline itself stays in AspNetCore (JC-2 unchanged).
- JC-16 — **HTTP sessions are request-scoped and NOT registered.** They hold no resource beyond the request, `Find` is for live pushes (#94 uses `IsLive`), and registering them would let a burst of HTTP POSTs from one peer evict that peer's live WebSocket session under the per-DID bound. FR-RR-03's bounds therefore govern WebSocket sessions; `SessionOpened`/`SessionClosed` never fire for HTTP. Reversible in ~10 lines (register before dispatch, unregister after `TakeResponse`) if the reviewer prefers the literal reading.
- JC-17 — **Per-endpoint fallback when the host did not register the registry/guard.** `Map*` resolves `IReturnRouteSessionRegistry` / `IInboundReplayGuard` with `GetService`; when absent it builds one default per mapped endpoint (lazily, once) from the options present, and logs once (**amended by ADV-2:** one default per application, shared by all its mapped endpoints, so a request admitted on one is a duplicate on the others). Hosts that wire the dispatcher by hand (cookbook Q/R, hand-rolled containers) keep working and stay replay-protected; the documented path is `AddDidComm`, which makes one shared instance that handlers can also inject. Mirrors the existing `?? new DidCommReceiveOptions()` fallback.
- JC-18 — **Legacy callback overloads are untouched** (no session, no replay): they cannot open sessions and host no mediator handlers, and applying FR-RR-08 there would drop authenticated mediator-typed messages for apps that implement those protocols in their own callback. Documented in their XML docs; #95 uses the registry-aware endpoints.
- JC-19 — **No `DidCommBuilder` configure helpers** in this issue; options go through `Services.AddOptions<T>().Configure(...)` like `DidCommReceiveOptions`. #95's `MediatorOptions` is the composed surface.
- JC-20 — **`thread` on an existing WS session downgrades it to `None`** (surfaced as `Thread` on the context): a peer explicitly asking for thread-scoped routing is not asking for "all"; pushing everything would exceed its request. FR-RR-05's "the session mode changes only when a later message carries `return_route`" is respected; FR-RR-03 "`thread` opens no session" is respected. Re-visit when a protocol needs `thread` (§15.2).
- JC-21 — **Eviction close is sent by the writer task via `CloseOutputAsync`**, the receive loop finishes on the peer's close frame, with a 5 s backstop that cancels the connection. Cancelling `ReceiveAsync` directly would abort the socket without a close frame, which FR-RR-03's "the peer observes it" wants to avoid.
- JC-22 — **Replay drop logging is rate-limited uniformly** (Warning for the first and every 1000th per admission outcome, Debug per drop with the id) because every in-scope sender is authenticated but a single enrolled peer can still flood; `Saturated` / `MessageIdTooLong` are additionally counted on the guard (`SaturationCount`) as the FR-RR-08 "metric".
