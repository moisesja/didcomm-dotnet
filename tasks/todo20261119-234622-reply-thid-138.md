## Design (our implementation choices, with reasons)

1. **One internal helper in Core**: `DidComm.Threading.ThreadIds.ResponseThreadId(Message request)`
   returns the request's `thid` when it declares one, else its `id`. Same name and meaning as the
   mediator's public `CoordinateMediation.ResponseThreadId`. Internal: no public API change, no new
   `InternalsVisibleTo` grant (Core already grants the test projects).
2. **A declared `thid` that is not a valid thread id is refused, not ignored.** On the wire path,
   unpack's `Message.Validate` already refuses it (an empty, whitespace or non-unreserved `thid`), so
   nothing changes there. A hand-built message passed to `TrustPing.CreateResponse` or to a handler
   directly is not validated; for it the helper throws `MalformedMessageException` with a message that
   quotes no value (D7). Reason: L15 says `thid` MUST meet `id`'s constraints, so an invalid one is
   spec-invalid input; falling back to `id` would silently move the reply to another thread (L-074).
   We check `Thid is null` (not `IsNullOrEmpty`), so an empty `thid` is refused like any other invalid
   one; this matches the dispatcher's `Thid ?? Id`.
3. **The value is echoed verbatim** (no case change): the requester compares (threading.md L9).
4. **No `pthid` on the reply**, as today (pinned by a test). Trust Ping and Discover Features are
   two-party protocols; L31 says the first child message is enough, and the reply is never that.
5. **The dispatcher keeps its inline `Thid ?? Id`** (the thread-state key); sharing the helper would
   change nothing on a validated message and add a throw on synthetic input. The mediator's two public
   `ResponseThreadId` helpers stay as they are (out of this issue).

## Review

### Sweep and design (architect pass, reconciled)

- The two sites the issue names are the only defect sites in `src/`; the mediator's answers, the
  problem reports and the dispatcher's thread key were already right. Two sample handlers (cookbook
  section X, sample 07) taught the same defect: fixed, same rule.
- Reconciliation: the architect recommended `IsNullOrEmpty(thid) ? id : thid` (as the mediator does).
  We chose `thid is null` plus a refusal of a declared invalid `thid` (design call 2): an empty `thid`
  is spec-invalid (threading.md L15), and falling back to the `id` would be the kind of fallback L-074
  rules out. Unpack already refuses it, so only hand-built messages see the difference.

### QA

- 30 more cases (`ResponderReplyThreadEnvelopeTests`, `ReturnRouteReplyThreadTests`, a sibling in
  `DiscoverFeaturesRoundTripTests`, siblings in `DiscoverFeaturesClientTests`); with the 81 Core cases
  above, 111 in all.

  no-`thid` control passes; green after restore and rebuild (L-071). The correlator tests were proven
  with a second mutation (the client matching any pending query whatever its `thid`).
- No product defect.

### Adversarial

- Wire `thid` values (empty, whitespace, CR-LF, ESC, non-ASCII, `/`, numbers, objects, arrays,
  booleans) are refused at unpack, before any responder; the endpoints log the exception type only,
  and no probe value reached a log line. `"thid": null` is "no thid".
- Our clients cannot be mis-completed by a peer that picks our pending query id as its `thid`: the
  reply is outbound to the authenticated sender, and our correlators take only authenticated inbound
  answers from the queried peer.
- Routing is unchanged: nothing in `src/` routes a reply by its `thid`.
- Info, fixed: the architecture doc and DD-11 claimed the thread rule for every reply; a problem
  report starts a child thread (problems.md L83), and the refusal of an invalid hand-built `thid` is
  Core's two responders only.
- Info, declined (pre-existing, hand-built messages only): with no `thid` and an invalid `id`, the
  reply builder's refusal names the field `thid` and quotes the value; with a null `id` the reply has
  no `thid`. Unchanged by this PR.
