## Design (our implementation choices, with reasons)

1. **One internal helper in Core**: `DidComm.Threading.ThreadIds.ResponseThreadId(Message request)`
   returns the request's `thid` when it declares one, else its `id`. Same name and meaning as the
   mediator's public `CoordinateMediation.ResponseThreadId`. Internal: no public API change, no new
   `InternalsVisibleTo` grant (Core already grants the test projects).
2. **A declared `thid` that is not a valid thread id is refused, not ignored.** On the wire path,
   unpack's `Message.Validate` already refuses it (an empty, whitespace or non-unreserved `thid`), so
   nothing changes there. A hand-built message passed to `TrustPing.CreateResponse` or to a handler
   directly is not validated; for it the helper throws `MalformedMessageException` with a message that
   quotes no value (D7). Reason: L15 says `thid` MUST meet `id`'s constraints, so an invalid one is
   spec-invalid input; falling back to `id` would silently move the reply to another thread (L-074).
   We check `Thid is null` (not `IsNullOrEmpty`), so an empty `thid` is refused like any other invalid
   one; this matches the dispatcher's `Thid ?? Id`.
3. **The value is echoed verbatim** (no case change): the requester compares (threading.md L9).
4. **No `pthid` on the reply**, as today (pinned by a test). Trust Ping and Discover Features are
   two-party protocols; L31 says the first child message is enough, and the reply is never that.
5. **The dispatcher keeps its inline `Thid ?? Id`** (the thread-state key); sharing the helper would
   change nothing on a validated message and add a throw on synthetic input. The mediator's two public
   `ResponseThreadId` helpers stay as they are (out of this issue).
