## Spec lines relied on

**Sources:**
- DIDComm v2.1: `decentralized-identity/didcomm-messaging@c78bcc425f9546200e77151d2752b8317d3eae00`, `docs/spec-files-v2.1-snapshot/`.
- Message Pickup: `decentralized-identity/didcomm.org@a26926c`, `site/content/protocols/messagepickup/{3.0,4.0}/readme.md`.

**Attachment ids are opaque and unique per mediator. Using one as a key deduces nothing else.**
- 3.0 L170: "The `id` is an opaque value, and the recipient should not deduce any information from it, except that it is unique to the mediator. The recipient can use the `id`s in the `message_id_list` field of `messages-received`."
- 4.0 L257: the same, with "**SHOULD NOT**".
- Hence the key includes the mediator DID (D-3), and ids compare exactly (D-8).

**A message the client does not open is not acknowledged, so it stays queued.**
- 3.0 L145: "Delivered messages **MUST NOT** be deleted until delivery is acknowledged by a messages-received message."
- 4.0 L212: the same.
- 3.0 L177: "After receiving messages, the `recipient` sends an acknowledge message indiciating which messages are safe to clear from the queue."
- 4.0 L268: "After receiving messages, the `recipient` **MUST** send an acknowledge message indiciating which messages are safe to clear from the queue."
- A message held back or failed is not safe to clear, so it is never in `message_id_list`.
- A delivery with nothing safe to clear sends no `messages-received`. That is main's behaviour since #96/#100, and #111 does not change the rule.
- **No conflict** with a client that declines to open a delivered message for a while: the mediator keeps it (L145/L212) and delivers it again.

**Live mode.**
- 4.0 L308: "If _Live Mode_ is active, messages still **MUST** be delivered via a `delivery` message and the `recipient` **MUST** send an acknowledgement message `messages-received`. If a message is not acknowledged, the message **MUST** be added to the queue for later pickup."
- A held-back live push is not acknowledged, so the mediator queues it again.
- 4.0 L304 and 3.0 L203: queued messages "**MUST** still be requested with `delivery-request` messages". So the drain stays the way queued messages arrive.

**Message ids compare ignoring case; attachment ids have no case rule.**
- threading.md L9: an `id` "SHOULD be written in lower case but MUST be compared case-insensitively". The duplicate filter's key already folds the inner message id.
- message_structure.md L174 (attachment `id`) gives "unreserved URI characters" and no case rule.

**The sender key in the outer envelope.**
- encryption.md L119: "the unpacking process on his end resolves the `skid` protected header value using Alice's DID document's `keyAgreement[0]`".
- L140: `apu` "MUST contain the `skid` value base64 RawURL (no padding) encoded".
- L147: "authcrypt implementations MUST be able to resolve the sender kid from the `apu` header if `skid` is not set."
- message_structure.md L23: anoncrypt(authcrypt(plaintext)) "hides the `skid` header in the authcrypt envelope".
- How we use this:
  - The client reads the protected header (unauthenticated) only to pick an accounting partition (D-1).
  - It changes nothing about what is opened or how.
  - `apu`-only authcrypt is still opened and resolved exactly as Core does today. Only its accounting partition is the anonymous one.

**Verdict.** No spec text conflicts with this design. No wire behaviour changes:
- the same requests;
- the same acknowledgement rule;
- the same opening rule.

## Invariants (write these first; every bound says what it counts, when it is taken, when it is released)

Restated on 2026-11-25 for the design as built after fix rounds 2 and 3 (owner decisions C, D, E, F and G). Ids are stable, because code comments and the other docs cite them: a withdrawn invariant keeps its number and says why it went, and what the rounds added is I-22 to I-25. The first form of this section is in this file's history, up to `27b715e`.

**Notation:**
- B = `UnpackTimeout` (20 s by default): the budget of one delivery;
- F = max(1 tick, B/4) (5 s): how much of the budget must be left for a message to start;
- A = `StartAllowance` = F/2 (2.5 s);
- W = `FetchConcurrency` = 16: how many messages of one delivery are opened at the same time;
- T0 = 30·B (10 min); Cap = Q·B = 256·B (about 85 min);
- C = `MaxReserved` = 256; P_named = `MaxPerSender` = 16; P_anon = `MaxPerAnonymous` = 16;
- Q = 256 entries per memory partition; R = 256 memory partitions;
- τ is withdrawn (D-6).

### Opening a delivery

**I-1 Container bound (ADV3-2, the pool-thread residual).**
- At most C = 256 host unpack calls are started and not yet ended per container (channel). The number is owner decision D ("Raise to 256, document (Recommended)").
- Counts: one host unpack call (the DID and secrets resolvers behind it), from before its work item exists until it ends for any reason, whether its worker still waits for it or its delivery has ended and let it go.
- Taken: atomically under `UnpackReservations._gate` (`TryTake`: the check and the take are one step), before the host work item exists. A refusal starts nothing (D-7).
- Released: exactly once (`Reservation.Release`), by whoever is first:
  - the worker, as soon as the call it awaited has ended and before it takes its next message (D-13);
  - a continuation on the host task, when the call ends after its delivery did (including a call whose token was cancelled before it ran);
  - directly, when the work item is never created.
- A call that was cancelled keeps its reservation until it ends, also after its delivery's result is set (R-13).

**I-2 Partition bound (ADV2-2).**
- Per (mediator, mailbox, sender key), host calls started and not ended number at most P: 16 for a named sender, 16 for the mailbox's anonymous partition (`UnpackReservationsTests.A_named_sender_gets_sixteen_per_mailbox_and_the_anonymous_partition_sixteen_of_its_own`).
- Taken and released with I-1, in the same handle, under the same lock.
- P for a named sender is not below W (I-23).

**I-3 No late host code (ADV4-3).** A host work item is created only under the delivery's `_gate` while the delivery is open, with the budget's token. There is one token per delivery; no message has a token of its own. If the token is cancelled before the item runs, the unpack delegate does not run (`DeliveredUnpackAdv4Tests.ADV4_3_a_message_whose_worker_was_starting_it_when_the_shutdown_came_never_has_its_host_code_started`).

**I-4 Bounded retention (ADV4-2).**
- A host work item references only (the unpack delegate, the packed text, the budget's token, the unpacker's clock).
- Its release continuation references only its reservation handle, which references its owner and its partition.
- While a delivery is open, the budget's token references it: through the delivery's own registration on the token, and through its workers' waits. The registration holds a link (`Delivery.EndLink`), not the delivery, and the link is cleared when the delivery ends; the workers' waits end with the delivery. From then on, host code that still runs, or still holds a registration of its own on the token, keeps nothing of the delivery reachable. The link is ours (engineer U2's mechanism).
- Tests: `DeliveredUnpackAdv4Tests.ADV4_2_an_unpack_that_blocks_its_thread_keeps_nothing_of_its_delivery_reachable_after_the_result_was_returned`, `UnpackSlotsQa2Tests.Host_code_that_keeps_a_registration_on_its_token_after_its_call_ended_keeps_nothing_of_the_delivery_reachable`.

**I-5 Budget.** A delivery's result is set no later than its budget timer, the caller's cancellation or the shutdown. Unchanged. That a delivery sets its result whatever its messages do and whatever ends it: `DeliveredUnpackEndingsRt3Tests.Whatever_its_messages_do_and_whatever_ends_it_a_delivery_sets_its_result_and_leaves_nothing_behind`. With a resolver that blocks its thread the budget's own timer can itself be delayed (R-8 b).

**I-6 The start rule.**
- A message starts only if e ≤ B − F, where e is the time since the budget started, read once and clamped to [0, B]. Otherwise it fails as out of time before its turn: no host call is created and nothing is remembered.
- A message has no share and is not cut. Once started it runs until it opens, fails, or the delivery ends (owner decision E: "Remove per-message limits (Recommended)").

**I-7 (withdrawn).** The share formula (a message's share sized from the time left). Withdrawn in fix round 2 by owner decision E, which replaced the share-sizing direction of #111.

**I-8 Fast failures do not hold up the delivery (restated without τ).**
- A message that fails on its own gives its worker back at once, and that worker takes the next message. The start rule (I-6) alone decides whether a message starts.
- Tests: `DeliveredUnpackAdv3Tests.ADV3_3_junk_that_fails_at_once_leaves_an_honest_message_first_the_time_to_open`, `SlowSenderFetchQa1Tests.ADV3_3_an_honest_message_among_ninety_nine_fast_failures_opens`.
- The first form rested on τ and on four at a time. Both are gone.

### The slow memory

**I-9 What is written (owner decision C, "Every failure, fair to late starts (Recommended)", under owner decision E).** The memory of messages that did not open is written in these cases, and only these:
- **S1, it failed on its own.** The host call's code ran, and the call failed while the delivery was not being ended (I-22). The message is struck, whatever the duration and however late it started.
- **S2, it had the whole budget (the coordinator's call).** The budget's own timer ended the delivery (not the caller, not the shutdown), the message had no outcome yet, and its code had started within A of the budget's start, both readings taken from the injected clock. The message is struck. `StartAllowance` = F/2 began as ours in fix round 1 and was kept by the coordinator's call in fix round 2.
- **Opened.** The message is forgotten.
- **Nothing else writes:** not a refusal, a held-back message, a malformed one, one that did not start, one whose code started later than the allowance, one whose start reading is below the budget's start, nor one that was running at the caller's cancellation or the shutdown. An entry still inside its pause gets no further strike (RT1B-2).
- Whoever records an outcome makes its write, and every write of a delivery is made before its result is set.
- What S1 means for an honest sender: a message that failed on its own is held back for its first pause (ten minutes at the default), an honest one included.
- Tests: `DeliveredUnpackSlowSenderTests.A_failure_is_remembered_whatever_its_duration`, `…A_failure_of_a_message_that_started_late_is_remembered`, `…A_never_opening_message_is_remembered_at_the_budgets_end_only_if_its_code_started_within_the_start_allowance`, `…A_never_opening_message_whose_start_reading_is_below_the_budgets_start_is_not_remembered`, `…A_message_that_started_late_behind_others_is_not_remembered_at_the_budgets_end_and_is_at_the_next_delivery_where_it_starts_first`, `SlowMemoryQa1Tests.The_callers_cancellation_or_the_shutdown_remembers_none_of_the_messages_running`.

**I-10 What is keyed.**
- Partition = (mediator DID, mailbox DID). Both come from the host's call.
- Entry = SHA-256/128 over (the partition's key, the attachment id's exact UTF-16 code units). There is no case folding: ids that differ only in case are different messages (D-8; `SlowMemoryFetchQa1Tests.Attachment_ids_that_differ_only_in_case_are_different_messages_on_the_fetch_path`).
- Nothing a sender writes enters a key or decides a write: not the `skid`, `from`, the bytes or the sender DID. Writes are decided only by our timers, readings and outcomes.

**I-11 Bounded.**
- At most R partitions × Q entries. An entry is added by a strike, and removed when its message opens or by eviction; a partition whose last entry is forgotten is removed.
- Inside a partition, the least recently *seen* entry is evicted, ordered by a sequence counter, not a clock.
- Whole partitions are evicted least recently used.
- Each operation is O(Q + R) under one leaf lock.
- Tests: `SlowMemoryTests.M3_churn_in_one_mailbox_evicts_only_that_mailboxs_entries`, `…M4_an_entry_seen_in_a_delivery_outlives_one_struck_after_it_but_seen_less_recently`, `…M5_one_partition_more_than_the_bound_drops_the_least_recently_used_one`.

**I-12 Fail open on clocks.**
- An entry holds a message back only while struckAt ≤ now < struckAt + backoff(strikes), with backoff(k) = min(Cap, T0·2^(k−1)): 10 minutes after the first strike, doubling, at most 256·B (about 85 minutes).
- A clock reading below the one a message was last struck at counts as due, so after the host clock steps back the message is opened once more. If it fails again, that is the same slow episode: no strike is added, and it is held back for the same pause again, counted from that failure, not for the next, doubled pause. So a step back can make a message due later than without it (in the measured case half a minute: minute 30.5 instead of minute 30), and each further step back costs one more opening. No general bound is stated for this.
- That a repeat failure after a step back is the same episode is the coordinator's specification of fix round 2 (RT2B-2). That the entry then keeps its strikes and takes the lower reading is ours (engineer S2's reading).
- Tests: `SlowMemoryTests.M2_a_reading_below_the_strikes_is_due_and_a_stepped_back_clock_never_holds_back_past_the_pause`; `SlowMemoryClockStepTests.A_repeat_failure_read_below_the_last_strike_keeps_the_strikes`, `…A_repeat_failure_read_below_the_last_strike_is_stamped_with_the_lower_reading`, `…After_a_step_back_the_message_is_due_one_pause_after_its_repeat_failure`, `…A_clock_that_steps_back_five_times_costs_one_opening_per_step_and_the_pause_keeps_its_length`; `SlowMemoryRt2BTests.After_a_clock_step_back_a_message_that_fails_again_is_held_back_for_the_same_pause_again_and_not_for_the_doubled_one`.

**I-13 Held back.**
- Before any worker starts, the memory is asked once which of the delivery's messages are in their pause. Each of those gets its failure then.
- A held-back message takes no reservation, runs no host code and is not acknowledged.
- A delivery made only of held-back messages returns at once, with no timer.

**I-14 The sender key never over-attributes.**
- The named partition is `DidSubjectOf(skid)`, and only when the protected header's `alg` is ECDH-1PU+A256KW and `skid` is present (read with `JweParser.PeekRecipients`, the call Core makes).
- Otherwise the message is anonymous: anoncrypt, `apu`-only, unreadable, or anything else.
- Core resolves exactly `DidSubjectOf(kid)`, so a lookup charged to S resolves S.
- Tests: `SenderPartitionTests.An_authcrypt_envelope_with_a_skid_counts_against_the_skids_DID_subject`, `…T9_an_ECDH_ES_envelope_that_carries_a_skid_is_anonymous`, `…T10_an_authcrypt_envelope_that_names_its_sender_only_in_apu_is_anonymous`, `…An_anoncrypt_envelope_is_anonymous`, `…Anything_else_is_anonymous_and_never_throws`.

### The live stream

**I-15 No reading comparisons (ADV4-4).** Every "due" decision is the fired flag of an alarm the stream armed (a `TimeProvider` timer). There is no `GetElapsedTime` comparison anywhere in the stream (the two `PickupClientLiveAdv4Tests.ADV4_4_*` tests).

**I-16 One predicate.**
- `WaitAsync` returns without awaiting iff `NextAction() != None`, the same function the loop dispatches on.
- Every action changes the state that made it actionable, so the loop cannot spin.
- The hand-over between the wait and an alarm: `PickupClientLiveSchedulingTests.An_alarm_that_fires_after_the_wait_published_its_wake_source_and_before_it_looks_again_still_runs_the_cycle`.

**I-17 R1-1 kept.** The cycle alarm is armed only at a drain's end or after a failure, never while draining (`PickupClientLiveAdv5Tests.A_fifty_round_drain_slower_than_the_interval_is_never_pre_empted_and_the_next_cycle_is_due_one_interval_after_its_last_answer`).

**I-18 The run of failures (ADV5-3; restated for owner decisions B1 and F).** A failed step adds to two things, and they are let go by different events.
- **The failure count** sets the back-off (1 s, doubling to 30 s).
  - Counts: failed steps in a row.
  - Taken: one at each failed step (a cycle request, a drain round or an acknowledgement).
  - Released (set to zero): only at a drain that ends, and at a drain round that brings something new. Never at a push, never at an accepted acknowledgement (owner decision F: "Only cycle success resets (Recommended)").
- **The give-up alarm.**
  - Armed: at the first failure since it was last let go, for `RequestTimeout` plus 30 s (60 s in all at the defaults).
  - Let go: at a drain that ends, at a drain round or a push that brings something new, and at an acknowledgement the mediator accepted, which under Message Pickup 4.0 is one that was sent (owner decision B1, "Push keeps the wait (Recommended)", as refined by F).
  - A retryable failure ends the stream only after the give-up alarm has fired.
- Measured, with every cycle request failing, whatever pushes arrive and whatever acknowledgements are accepted: exactly 24 cycle requests in ten minutes when each is refused at once (at 0, 1, 3, 7, 15, 31 s, then every 30 s), exactly 12 when each times out after `RequestTimeout` (`LiveStreamRt2CTests.With_every_cycle_failing_and_acknowledgements_accepted_cycles_stay_at_one_per_growing_back_off`, `…With_every_cycle_timing_out_and_acknowledgements_accepted_cycles_stay_at_one_per_growing_back_off`). What restarts the back-off: `PickupClientLiveSchedulingTests.Only_a_drain_that_ends_or_a_drain_round_that_brings_something_new_starts_the_back_off_again`.
- When the failed step is an acknowledgement and nothing else is ready, the acknowledgement is sent again first, and a cycle follows only once it is accepted. Measured, with every cycle request answered, every acknowledgement refused and no push after the first delivery: one live-on request in ten minutes, and the stream ends with the refusal at 61 s (`LiveStreamBackoffRt3Tests.With_cycles_answered_every_acknowledgement_refused_and_no_push_after_the_first_delivery_no_cycle_request_follows_the_first_and_the_stream_ends_with_the_refusal`).
- What a mediator that refuses acknowledgements causes: with cycle requests answered, acknowledgements refused and accepted in turn, and pushes every one or two seconds, one cycle follows each refused acknowledgement (300 in ten minutes). The mediator's pushes drive that rate; it is not a bound on the client (`LiveStreamBackoffRt3Tests.With_cycles_answered_and_acknowledgements_refused_and_accepted_in_turn_one_cycle_follows_each_refused_acknowledgement`). The coordinator's call: this does not reopen decision F.

**I-19 The drain's end (ADV5-4, QA2-3; restated for owner decision F).**
- A drain round that brings nothing new ends the drain: every message in it is one the stream holds, or one that came in a delivery this drain took.
- **The per-drain set.**
  - Counts: the 128-bit keys of the attachment ids of the deliveries the current drain took (a round's answer, or a push taken in its turn between two rounds). That the set holds deliveries taken, not failures yielded, is ours (engineer S2's reading).
  - Taken: when a delivery is taken while a drain runs. A push taken during a back-off or between drains adds nothing.
  - Released: only when a drain ends. Not when a cycle starts, and not at a failed step.
  - Bound: `MaxDoneThisDrain` = (50 rounds + 49 pushes) × 10 = 990 (`LiveStreamRt2CTests.With_a_full_push_at_every_turn_the_per_drain_set_stays_within_its_stated_bound`).
- **The round count** (at most 50 rounds that bring something new, `MaxDrainRounds`) is counted until a drain ends, across the cycles of a drain whose steps fail, and starts again when a drain ends.
- A failed step does not end a drain: the stream backs off, and the cycle that retries goes on with the same drain (ours, engineer S2's reading). So a round that brings back only what was reported since the last drain ended is not something new, whichever cycle reported it (`LiveStreamRt2CTests.A_round_that_brings_back_only_the_previous_cycles_failure_does_not_restart_the_back_off`, `…What_a_drain_reported_is_not_something_new_until_that_drain_ends_and_is_new_again_after_it`).

**I-20 One alarm per arming.**
- Each arming makes a new alarm and disposes the one it replaces.
- A callback only sets its own flag and pokes the wake source.
- A late callback of a replaced alarm changes no decision (`PickupClientLiveSchedulingTests.A_replaced_alarms_late_callback_runs_no_cycle_and_no_acknowledgement_before_the_back_off_ends`).

### What fix rounds 2 and 3 added

**I-22 The token-state rule (L-077; the coordinator's call, fix round 2).** Whether a host call, a request or an endpoint lookup that did not succeed was cancelled or failed on its own is decided by the state of the tokens when the outcome is observed, never by the type of what was thrown. Host code may report its cancellation as a failure of its own, and may do so from a callback that runs before ours.
- **The unpacker.** A delivery is being ended when its budget's token, the caller's token or the shutdown is cancelled (`Delivery.BeingEnded`). A worker that observes a call that did not open while the delivery is being ended records nothing and takes no further message; the delivery's end records the message. Reading the caller's token and the shutdown as well as the budget's token is ours (the orchestrator's call). Tests: `DeliveredUnpackTokenStateTests.A_failure_reported_when_the_caller_cancels_leaves_the_result_cancelled_and_nothing_remembered`, `…A_failure_reported_when_the_budget_ends_for_a_late_started_message_is_a_timeout_and_is_not_remembered`, `…A_failure_reported_when_the_budget_ends_for_a_message_that_had_the_whole_budget_is_a_timeout_and_is_remembered`, `…A_failure_reported_from_a_callback_on_the_callers_token_or_on_the_shutdown_token_leaves_the_result_cancelled_and_nothing_remembered`, `…A_worker_takes_no_further_message_once_the_delivery_is_being_ended`.
- **The live stream.** A request that fails once the caller's token is cancelled ends the stream as cancelled, whatever it reported (`LiveStreamCancelledStepTests`). Ours (engineer S2's reading).
- **The channel.** A send or an endpoint lookup that fails once its call is being ended (the request's deadline passed, the caller cancelled, or the container was disposed) ends the call as what ended it, whatever the host code reported. A Debug line names the type of what was reported, never its text (`MediatorClientChannelTokenStateTests`; `MediatorClientChannelTokenStateRt3Tests.What_the_host_code_reported_while_its_call_was_being_ended_is_named_in_the_log`, `…No_log_line_carries_the_text_of_what_the_host_code_reported_while_its_call_was_being_ended`). Reading the caller's token and the disposed flag as well as the deadline's token is ours (the orchestrator's call).
- **Through `FetchAsync`:** `PickupClientFetchTokenStateTests`.
- Where the rule ends: R-16.

**I-23 Sixteen at once, and the sender's bound never below it (owner decision G: "Open 16 at once (Recommended)").**
- Counts: the messages of one delivery that are being opened at the same time. A delivery has min(16, its messages that are not held back) workers.
- Taken: a worker takes the next message in delivery order, under the delivery's lock.
- Released: when that message's outcome is recorded (the worker then takes the next), or when the delivery is being ended (the worker stops; I-22).
- `MaxPerSender` is never below `FetchConcurrency`, and the two change together (`DeliveredUnpackSixteenAtOnceTests.A_partitions_bound_is_not_below_what_one_delivery_opens_at_once`). Ten and sixteen one-second messages from one sender in one delivery all open and none is refused (`…Messages_of_one_sender_in_one_delivery_each_taking_a_second_all_open_and_none_is_refused`).
- What a host sees: a DID resolver gets up to sixteen lookups at once per fetch or per live delivery, and a resolver that blocks its thread holds up to sixteen thread-pool threads per delivery (R-8).
- What it costs: sixteen messages that never open hold every worker for the budget, and the message behind them gets its turn in the next delivery (R-3; `…Sixteen_never_opening_messages_of_one_sender_hold_every_worker_for_the_budget_and_the_message_behind_them_gets_its_turn_in_the_next_delivery`). A sender's seventeenth and later messages are refused at once while its sixteen lookups run, and another sender's message behind them opens (`…A_senders_seventeenth_and_later_messages_are_refused_at_once_while_its_sixteen_lookups_run_and_another_senders_message_behind_them_opens`).

## Mechanisms (files)

Restated on 2026-11-25 from the code as built. The first form of this section is in this file's history, up to `27b715e`.

**Internal, in `src/DidComm.Mediator.Client/Client/Internal/`:**
- `DeliveryScope.cs`: `DeliveryScope(MediatorDid, LocalDid)` and `DeliveredInput(Id, Payload)`. The 128-bit key of a scope is `SlowMemory.ScopeKeyOf`.

- `UnpackReservations.cs`: I-1 and I-2.

  - `TryTake`, and a `Reservation` that releases exactly once: `Release` (the worker's call) or `ReleaseWhen` (a continuation on the host task, which observes the task's exception).
  - A refusal changes nothing else: it is not counted, and it ends no call that is running (`DeliveredUnpackNoPerMessageLimitTests.A_take_refused_for_a_running_messages_partition_does_not_end_it`, `…A_take_refused_for_the_container_does_not_end_a_running_message`).
- `SlowMemory.cs`: I-9..I-12.
  - One leaf lock.
  - `HeldBack(scope, ids)` takes one lock per batch and refreshes "seen"; `Strike`, `Forget`.
  - The constructor takes (TimeProvider, T0, Cap, Q, R) so tests can set them.
- `Alarm.cs`: `Start(TimeProvider, TimeSpan, poke)`, `AlreadyFired`, `Fired`, `Dispose`.
- `DeliveredOutcome.cs`: the result of opening one message. It carries the flag of I-24 from the unpacker to `PickupItem`; the fetch path and the live stream pass it on as it is.

**`DeliveredMessageUnpacker.cs` (I-1..I-13, I-22, I-23).**
- Entry point: `UnpackAllAsync(DeliveryScope, IReadOnlyList<DeliveredInput>, requestId, ct)`. Test seams: `Settled`, `Opening`, `Reserved`.
- The pre-pass asks the memory which messages are held back (I-13).
- One budget per delivery, a `GuardedDeadline` linked to the caller's token and to the shutdown. Up to sixteen workers take the other messages in delivery order. Each worker runs, for each message:
  1. strict UTF-8 (a message that is not, or is empty, fails as malformed);
  2. the start rule (I-6);
  3. `SenderPartition.Of`;
  4. `TryTake` (a refusal fails the message at once);
  5. under `_gate`, and only while the delivery is open: create the host call (`HostCall`) as a thread-pool work item with the budget's token, `Task.Factory.StartNew(static …, HostCall, token).Unwrap()`. The call records the clock's reading when its code starts, as its first action;
  6. `ReleaseWhen`;
  7. wait for the call through the budget's token;
  8. the outcome, by I-22: opened (release, success, `Forget`); not opened while the delivery is being ended (the worker records nothing and stops); failed on its own (release, failure, strike: S1).
- The delivery's end (`OnBudgetEnded`, on the budget's token): every message without an outcome is out of time. When the budget's own timer ended the delivery, each message that had the whole budget is struck (S2, `HadTheWholeBudget`). After the caller's cancellation or the shutdown nothing is struck and the result is cancelled.
- The result is set by the last recorder, after every memory write of the delivery.
- Removed in fix round 2 with the shares: `ShareDeadline.cs`; `ShareOf`, `ShareAt`, `_shares`, `OnShareDue`, `OutOfShare`, `RanItsShare`; in `UnpackReservations`: `TryExtend`, `Extended`, `TakeExtended`, both refusal counters, the cuts a refusal made, `Reservation.Cut`.
- Removed in the first build (against main): `_abandoned`, `Abandon`, `MaxAbandoned`, `_running`, the `lateForIt` branch.

**`IMediatorExchange.UnpackDeliveredBatchAsync(DeliveryScope, IReadOnlyList<DeliveredInput>, requestId, ct)`.** The channel passes it to its unpacker. `PickupClient.FetchAsync` and the stream build the inputs from the delivery's entries.

**`LiveDeliveryStream.cs` (its scheduler simplified, as the owner directed after #96's third stop; I-15..I-20, I-22).**
- Removed in the first build: `Due` and the reading comparisons, `_nextCycle`, `_notBefore`, `_failingSince`, `_draining`, the per-wait deadline, and the timestamps on taken ids.
- State:
  - `_phase` (Idle, Draining or BackingOff);
  - the alarms `_cycle`, `_flushAge` and `_giveUp`;
  - `_wake`;
  - `_failures` (the count that sets the back-off) and `_drainRounds`;
  - `_doneThisDrain` (the per-drain set, I-19);
  - `NextAction()`, `LetGiveUpGo()`, `RestartBackoff()`, `Poke()`.
- `Failed` and `DrainDone` are the only places the cycle alarm is armed (I-17). `DrainDone` is the only place the per-drain set and the round count are let go (I-19).
- A step's failure is caught by the caller's token's state first, then by whether a retry can fix it (I-22).
- The turn rule (ADV3-1) and R1-1 are kept as invariants.

**`MediatorClientChannel.cs` (I-22, I-25; unpublished).**
- `BeingEnded(deadline, ct)` reads the deadline's token, the caller's token and the disposed flag. What a send or an endpoint lookup throws while it is true ends the call as the disposal, the caller's cancellation or the timeout, the first of them that is true in that order, and is named in one Debug line by its type only.
- What a send throws while it is false is the request's own failure. The request's terminal compare-and-swap (`PendingRequest`) decides between it and an answer.

**Locks (read from the code; no test pins the lock order).**
- `Delivery._gate` protects the delivery's position, why it was closed, the outcomes, the table of host calls and the count of recorders still writing. Work-item creation happens inside it; no memory write and no reservation call does.
- `UnpackReservations._gate` and `SlowMemory._gate` are leaf locks, not taken while `Delivery._gate` is held.
- The stream has no locks: it is single-consumer.
- No lock is held across an await or host code.

**Timers.**
- The budget: a `GuardedDeadline` on the injected `TimeProvider`. No message has a timer of its own.
- The stream's alarms: they set a flag and poke `_wake`. The pushes channel keeps `AllowSynchronousContinuations = false`, so no stream code runs on a timer thread.

## Decisions (architect's proposals, reconciled; all ours unless labelled)

Restated on 2026-11-25 for the design as built after fix rounds 2 and 3. Ids are stable: a withdrawn decision keeps its number and says why it went. Where an owner decision or a call of the coordinator's replaced a choice of ours, the entry says which. The first form of this section is in this file's history, up to `27b715e`.

- **D-1 Isolation key (ours).**
  - The key is (mediator, mailbox, `DidSubjectOf(skid)`), named only for ECDH-1PU with a `skid`; otherwise one anonymous partition per (mediator, mailbox).
  - What naming S in a `skid` costs S: junk that names S resolves S's own DID, then fails decryption without S's key. It costs S's partition only what S's own lookup costs.
    - Measured: messages that never open and name the honest sender's own key are passed in the same time as messages that name no sender, in every cell of the 96 (`SlowSenderFetchMatrixTests.The_message_behind_N_that_never_open_is_returned_in_the_cells_measured_time_within_the_restated_bound`).
    - An honest slow sender's message behind junk naming its key reaches the application within the bound (`PickupClientSlowSenderAcceptanceTests.An_honest_slow_senders_message_behind_junk_naming_its_key_reaches_the_application_within_the_bound`).
    - What lookups that have not ended cost S: R-13.
  - An ECDH-ES envelope with a forged `skid` goes to the anonymous partition, so it is not counted against the sender it names (`SenderPartitionTests.T9_an_ECDH_ES_envelope_that_carries_a_skid_is_anonymous`).
  - Rejected:
    - keying on `skid` whatever the algorithm (that spoof);
    - decoding `apu` (it would need a second header parser, a parser differential);
    - per-mailbox only (it fails the ADV2-2 acceptance).
  - Residuals: R-1 (many sender DIDs) and R-2 (the anonymous partition).
- **D-2 Back-off (ours).**
  - T0 = 30·B (10 min) and Cap = Q·B = 256·B (about 85 min). Cap was 180·B until fix round 1 (QA1-1). Both scale with `UnpackTimeout`, as the learning time does.
  - Whether T0 outlasts learning, as measured (the tables are under "Acceptance bound"):
    - At this library's mediator defaults (ten per delivery, a quota of 100, a 60-second lease), the message behind 99 that never open is returned after 200 s by a fetch loop and after 380 s by the live stream: inside the first pause.
    - At limit 4 a fetch loop takes 500 s behind 99: inside the first pause.
    - Learning outlasts the first pause in the live stream behind 99 at a 10 s lease (1380 s; the messages learned first are opened a second time from 640 s on) and in a fetch loop at limit 4 behind 255 (3200 s and 3120 s).
  - The architect's first estimates in this entry ("about 500 s" for any limit of 4 or more, "about 373 s" for the stream) were not measurements and are withdrawn.
  - Cap is the longest single pause of a remembered message. A message that failed on its own is held back for its first pause, ten minutes at the default, an honest one included (`DeliveredUnpackSlowSenderTests.A_failure_is_remembered_whatever_its_duration`, `SlowMemoryTests.M1_the_pause_doubles_with_each_strike_up_to_the_cap`).
- **D-3 Memory bounds and key (ours).** Q = 256 per (mediator, mailbox) partition (2.5× our quota) and R = 256 partitions; "about 4 MB worst case" was the architect's estimate and was never measured.
  - **The owner's key is "(mailbox DID, the mediator's attachment id)". We add the mediator DID to it.** Ids are "unique to the mediator" (3.0 L170), so another mediator could otherwise write an honest mediator's ids on slow junk (`SlowMemoryTests.M6_the_mediator_and_the_mailbox_are_in_the_key`).
  - Per-partition eviction means a hostile mediator's id churn evicts only its own partitions (`SlowMemoryTests.M3_churn_in_one_mailbox_evicts_only_that_mailboxs_entries`).
  - What an eviction costs: one more opening of that message at its next delivery.
  - What a restart costs: one more opening of each remembered message. With sixteen or more that never open in front in one delivery, a new process for each loop does not return the message behind them (measured: not in 12 runs; R-5).
  - Rejected: one global LRU (churn would evict other tenants' entries).
- **D-4 C, P and W.**
  - **C = 256 (owner decision D: "Raise to 256, document (Recommended)").** It was 64 in the first design (ours). It bounds the host calls that can be held (R-8).
  - **P_named = 16 and W = 16 (owner decision G: "Open 16 at once (Recommended)").** Both were 4 in the first design (ours).
    - The two move together: P_named is never below W (`DeliveredUnpackSixteenAtOnceTests.A_partitions_bound_is_not_below_what_one_delivery_opens_at_once`).
    - So a delivery does not refuse a sender's messages because of the calls it is itself running: ten and sixteen one-second messages from one sender in one delivery all open and none is refused (`…Messages_of_one_sender_in_one_delivery_each_taking_a_second_all_open_and_none_is_refused`).
    - Engineer G3 measured the other settings with that test: at [16 at once, 4 per sender] ten from one sender give 4 opened and 6 refused, and sixteen give 4 and 12; at [16, 15] sixteen give 15 and 1.
    - This is stated for lookups of the delivery before that have ended (R-13).
  - P_anon = 16 (ours): scoped to the mailbox.
  - The arithmetic under D and G: one sender at its bound in sixteen mailboxes, or sixteen senders at their bound in one mailbox, hold the container's 256 (`ContainerSharingRt1ATests.Residual_one_sender_keeping_sixteen_mailboxes_busy_holds_the_whole_container`, `UnpackReservationsSixteenRt4Tests.Sixteen_partitions_at_the_senders_bound_hold_the_whole_container_and_nothing_stays_counted_when_their_lookups_end`). The coordinator on that pin: "sixteen mailboxes at one sender's bound hold the container; 64 before — keep the pin. It follows from G and D."
  - All are reservations (I-1, I-2).
- **D-5 Floor F = B/4 (ours).**
  - F is how much of the budget must be left for a message to start (I-6). Half of it is the start allowance of S2 (I-9).
  - Its first role, a floor under a message's share, went with the shares (owner decision E).
- **D-6 (withdrawn). τ = (B − F)/25.** The threshold below which a failure was not remembered. Withdrawn in fix round 1 by owner decision C ("Every failure, fair to late starts (Recommended)"): a message that failed on its own is remembered whatever the duration.
- **D-7 Refusals fail at once and are not remembered (ours).**
  - A message that cannot reserve (C or P full) fails at once with "unpack capacity exhausted", is not acknowledged, and comes back.
  - Rejected: waiting for a slot. A waiting worker brings back same-delivery starvation and adds a wait queue.
- **D-8 Attachment ids compare exactly (ours),** as `DeliveryReader` and our mediator already compare them. Case folding could merge two distinct opaque ids and hold back an honest message. Message ids (the duplicate filter) still compare ignoring case.
- **D-9 Error texts (ours, D7: our request id only, never a wire value).** Each is a `TimeoutException`.
  - Held back: "…was not opened: it did not open when it was delivered before, and it is not opened again until its pause ends. It was not acknowledged."
  - Capacity (the text keeps "unpack capacity exhausted"): one variant for the partition, one for the container.
  - Out of time, two variants: the budget "ran out before its turn came", and it "ran out while it was being opened". On `98a32ac` the second is used once the message's host call has been created. **Pending (2026-11-25):** which of the two a message gets whose call was created and whose code never ran is restated with the flag's final form.
  - `OutOfShare` went with the shares.
- **D-10 Public surface (ours; restated).**
  - T0, Cap, F and the start allowance are derived from `UnpackTimeout`. C, P, Q, R and W are constants. No new option.
  - One public property on `PickupItem` was added in fix round 3 (the coordinator's call; see "Packages"). This entry read "No public API" until then.
- **D-11 The stream decides "due" by alarms (ours; the owner's "simplify" direction).**
  - A clock step now costs nothing: no early cycle, and no postponement (`PickupClientLiveAdv4Tests.A_clock_that_steps_back_forward_and_back_again_costs_no_extra_cycle` and the two `ADV4_4_*` tests).
  - The ADV3-5 and ADV5-1 regression tests change their expected counts toward fewer cycles. Their property, "no storm, no postponement", is kept.
- **D-12 Give-up stays time-based (ours).** The give-up alarm is armed at the first failure since it was last let go, for `RequestTimeout` plus 30 s (60 s in all at the defaults). A retryable failure after it has fired ends the stream. What lets it go is I-18. ADV5-2's documented rule is unchanged.
- **D-13 An honest but slow sender, with junk carrying its `skid` (ours; the coordinator's case).**
  - **The case:** S's DID takes 2–5 s to resolve, and junk names S in its `skid`.
  - **Lookups are not shared across messages.** Core's per-unpack key context keeps no cross-message state, by design. The client does not wrap the host's resolver either, so the design works the same with or without a resolver cache.
  - **What bounds the cost instead:**
    - P_named holds S's lookups at most 16 at a time per (mediator, mailbox) (owner decision G). It does not cap the load on S's own host (QA2-2, fix round 1; the first form of this entry said it did): each mailbox counts for itself, messages in a mailbox's anonymous partition can resolve S's DID as well, and spellings of the DID that differ count as different partitions.
    - A junk message that fails on its own is remembered after one opening, whatever it cost (S1). One that does not end is remembered at the budget's end when it had the whole budget (S2). Either is then held back for T0, so it costs one lookup per pause, not one per delivery.
  - **Why S's real message is not refused for its partition inside one delivery.** A worker gives back the reservation of a host call that has ended before it takes its next message. This is an exactly-once release, shared with the continuation. So the workers do not find S's partition full of their own finished calls (`DeliveredUnpackSlowSenderTests.A_senders_partition_never_refuses_inside_one_delivery_because_of_its_own_finished_calls`, `…A_senders_partition_never_refuses_inside_one_delivery_because_of_its_own_opened_calls`). Calls of another delivery for the same (mediator, mailbox) that are still running, or calls let go and still ending, do fill it: R-13.
  - **The bound.** S's real message reaches the application within the acceptance bound (`PickupClientSlowSenderAcceptanceTests.An_honest_slow_senders_message_behind_junk_naming_its_key_reaches_the_application_within_the_bound`). Messages that all name one sender, whose lookups end when cancelled and have ended before the next fetch, are learned as fast as messages that name none (`SlowSenderFetchRt2BTests.The_message_behind_one_senders_never_opening_messages_is_reached_within_the_restated_bound_as_fast_as_behind_messages_that_name_no_sender`).
  - **What remains:** R-3 as restated, and R-13. The first R-3 ("an S slower than its share is cut") went with the shares.
  - **Rejected:** a client-level single-flight lookup per DID. It would mean either a cross-message cache of key results (against Core's no-cross-message-state rule for key evidence) or wrapping the host's resolver. Neither is needed for the bound.

## Acceptance bound (measured figures, each with the test that prints it)

Restated on 2026-11-25. Until then this section was headed "architect's figures; QA verifies" and held the architect's estimates for the first design ("about 500 s", "about 6 min", "about 10 cycles"); it is in this file's history, up to `27b715e`. Every figure below is printed by the test named beside it, on the manual clock, and was re-run by the orchestrator on the built head (the integration branch `feat/slow-sender-111`). The comparison with the head before fix round 2 is under "Fix round 3".

**Assumptions:**
- N is the number of messages that never open in front of an honest one, N ≤ 256 (Q). At this library's mediator "any number" is 99: its quota of 100, less the honest one.
- Every one of the N is new to the client.
- **The lookups of one delivery have ended when the next one starts.** Every bound and figure below is stated on that condition. A delivery that starts earlier refuses what the sender's bound does not leave free and takes no time, and those messages wait for their next delivery, at most one lease. R-13 names the pins that show it.

**This library's mediator delivers at most ten messages per fetch at its defaults** (`PickupClientSlowSenderAcceptanceTests.At_its_defaults_this_librarys_mediator_delivers_at_most_ten_messages_per_fetch`: 30 queued, limit 100: 10, then 10). So at this library's mediator every message of a delivery starts when the delivery does.

**Fetch loop at this library's mediator** (`PickupClientSlowSenderAcceptanceTests.A_fetch_until_drained_loop_reaches_the_message_behind_ones_that_never_open_within_the_bound`, lines prefixed `A2 |`; the real mediator on a test server). Time until the honest message behind N that never open is returned opened. It is the same at a 60 s and a 10 s lease:

| limit | N 1 | N 16 | N 31 | N 99 |
|---|---|---|---|---|
| 4 | 20 s | 80 s | 160 s | 500 s |
| 10 | 20 s | 40 s | 80 s | 200 s |

- In every cell each message that never opens is opened once. There is no second learning pass, nothing is refused, and nothing is out of time before its turn.
- At this library's mediator defaults (ten per delivery, a quota of 100, a 60-second lease): behind 99 messages that never open, the message is returned after 200 s, ten fetches of one budget each.

**The 96 cells** (`SlowSenderFetchMatrixTests.The_message_behind_N_that_never_open_is_returned_in_the_cells_measured_time_within_the_restated_bound`, lines prefixed `C |`; a simulated mediator that honours the limit asked for). Seconds until the honest message is returned. Messages naming no sender, naming one other sender, or naming the honest sender's own key give the same time in every cell, so one table stands for all three:

| lease, limit | N 16 | N 31 | N 99 | N 255 |
|---|---|---|---|---|
| 60 s, 4 | 80 | 160 | 500 | 3200 |
| 60 s, 10 | 40 | 80 | 200 | 520 |
| 60 s, 16 | 20 | 40 | 140 | 320 |
| 60 s, 100 | 60 | 80 | 380 | 240 |
| 10 s, 4 | 80 | 160 | 500 | 3120 |
| 10 s, 10 | 40 | 80 | 200 | 520 |
| 10 s, 16 | 20 | 40 | 140 | 320 |
| 10 s, 100 | 20 | 40 | 140 | 360 |

The row "60 s, 100" is as measured: N 255 is lower than N 99 there.

**The bound.** It is fix round 1's restated bound, which applies again because at limits up to 16 a delivery starts all its messages. With ℓ the limit:
- for ℓ ≤ 16: L = ⌈N/ℓ⌉·B;
- for ℓ > 16: L = ⌈ℓ/16⌉·(⌈N/ℓ⌉·B + lease);
- the time is at most L when L ≤ T0 (30·B), otherwise at most 2·⌈log2(L/T0)⌉·L, for N ≤ 256.
- Of the 96 cells, 66 are exactly at the bound and 30 are below it: the six cells at limit 4 with N 255, where learning outlasts the first pause, and the 24 cells at limit 100. None is above.
- The 16 fetch cells at this library's mediator are exactly ⌈N/limit⌉ budgets.
- Where learning outlasts the first pause the bound is **checked by measurement, not proven**.
- No other formula is written for the fetch loop. The simulation over 1268 combinations that fix round 1 cites was of the design before decisions E and G and is not in the repository.

**One sender** (`SlowSenderFetchRt2BTests.The_message_behind_one_senders_never_opening_messages_is_reached_within_the_restated_bound_as_fast_as_behind_messages_that_name_no_sender`). Messages that all name one sender, whose lookups end when cancelled and have ended before the next fetch, are learned as fast as messages that name none.

**One sender whose lookups do not return** (`PickupClientSlowSenderAcceptanceTests.One_sender_whose_lookups_ignore_their_token_is_held_to_its_bound_of_sixteen_and_another_senders_message_is_reached_in_the_time_sixteen_take`, lines prefixed `A3 |`). Thirty messages from that sender in front:
- the sender is held to sixteen host calls, and fourteen are refused at once;
- another sender's message behind them is returned after 40 s at limit 10 and 80 s at limit 4, which is ⌈16/limit⌉ budgets.
- **Pending (2026-11-25):** what the same thirty cost when the lookups do honour their token. An engineer is adding that side to the same harness; no figure for it is written here until the test's name and its numbers are in.

**Sixteen of one sender in one delivery** (`DeliveredUnpackSixteenAtOnceTests`): the two tests under I-23.

**An honest slow sender.** Its message behind junk naming its key reaches the application within the bound (`PickupClientSlowSenderAcceptanceTests.An_honest_slow_senders_message_behind_junk_naming_its_key_reaches_the_application_within_the_bound`; D-13).

**Live stream, default `LivePollInterval`** (`PickupClientLiveSlowSenderTests.The_live_stream_reaches_the_message_behind_ones_that_never_open_within_the_live_bound`, lines prefixed `S7 |`). Time until the honest message is yielded, and the cycle it is yielded in:

| N | lease 60 s | lease 10 s |
|---|---|---|
| 1 | 20 s, cycle 1 | 20 s, cycle 1 |
| 16 | 40 s, cycle 1 | 100 s, cycle 2 |
| 31 | 140 s, cycle 2 | 260 s, cycle 4 |
| 99 | 380 s, cycle 4 | 1380 s, cycle 18; the messages learned first are opened a second time from 640 s on |

- The stream's cycle bound, which the same test asserts: the honest message is yielded in cycle K = ⌈(N + 1) / (10 · max(1, ⌊lease / B⌋))⌉ when learning fits in the first pause, and within 2K − 1 cycles when it does not. It is exact in seven of the eight cells and an upper bound in the eighth (cycle 18 against 19). **Checked by measurement, not proven.**
- The stream learns per cycle in proportion to the lease (R-10).

**A mediator that does not set delivered messages aside.**
- Such a mediator answers every fetch with the head of its queue. A fetch reaches the honest message only when it is within `limit` of the head. Otherwise the host discards failed items with `AckAsync` (R-6). A fetch made only of held-back messages returns at once, with no host code and no timer (I-13).
- **Pending (2026-11-25):** which failed items a host may discard, and what a host does after a fetch that brings none it may discard, are the flag's rule and are written here with its final form.
- The stream: one cycle sends at most two delivery requests when every round is answered with the same message that never opens (`PickupClientLiveAdv5Tests.ADV5_4_one_failing_message_at_a_mediator_that_does_not_lease_makes_every_drain_send_fifty_requests_and_yield_it_fifty_times`; the test's name describes the behaviour before #111, and the test asserts at most two).

- **R-2:** anoncrypted, `apu`-only and re-wrapped messages share one partition (16) per mailbox.
- **R-3 (restated).** The first R-3, "an honest sender slower than F is cut at F every time", went with the shares. In its place:
  - With no limit per message, sixteen messages that never open at the front of a delivery hold every worker for one budget. Those behind them in the same delivery run out of time before their turn and get their turn in the next delivery, where the sixteen are held back (`DeliveredUnpackSixteenAtOnceTests.Sixteen_never_opening_messages_of_one_sender_hold_every_worker_for_the_budget_and_the_message_behind_them_gets_its_turn_in_the_next_delivery`).
  - Only a delivery of more than sixteen has messages behind. This library's mediator delivers ten.
- **R-4:** more than 256 messages that never open queued in one mailbox, or more than 256 (mediator, mailbox) pairs, thrash the memory.
- **R-5 (restated; finding 1 of the red team on fix round 2; a documented residual by the coordinator's call).**
  - The memory lives in the process, and its longest pause is 256 budgets (about 85 minutes).
  - With sixteen or more that never open in front in one delivery, a loop run every two hours, a two-hour lease, or a new process for each loop does not return the message behind them (measured: not in 12 runs, not in two simulated days). Run again five minutes later in the same process, it does, in the second run.
  - This library's mediator delivers at most ten per fetch, so it takes another mediator.
  - Tests: `SlowSenderSpacedDeliveriesRt3Tests.Residual_with_sixteen_or_more_in_front_in_one_delivery_and_deliveries_further_apart_than_the_longest_pause_or_a_new_process_each_time_the_message_behind_is_not_returned`, `…With_sixteen_or_more_in_front_in_one_delivery_a_fetch_loop_run_every_five_minutes_in_one_process_returns_the_message_behind_them_in_its_second_run`.
- **R-6:** a mediator that does not set delivered messages aside still needs the host to discard failed items with `AckAsync`. **Pending (2026-11-25):** which failed items a host may discard is the flag's rule, written here with its final form.
- **R-7:** a `recipientDid` filter mismatch is not remembered: that message opened.
- **R-8 (extended).** Up to 256 host calls may be held by host code that does not return. A resolver that blocks its thread holds a thread-pool thread per lookup, up to sixteen per delivery. With such a resolver:
  - (a) messages can start later than the start allowance and are then not remembered at the budget's end; they are tried again;
  - (b) the budget's own timer can be delayed.
  - The measurements behind this are table A and the red team's F3, under "Fix round 3". **Pending (2026-11-25):** an engineer is committing them as opt-in measurements; until then no committed test prints them.
- **R-9 (withdrawn).** It read "a forward clock jump can strike a fast failure once". Removed with τ in fix round 1, and it stays removed. What is pinned instead: the start readings come from the injected clock, and a reading below the budget's start, or later than the start allowance, means nothing is remembered (`DeliveredUnpackSlowSenderTests.A_never_opening_message_whose_start_reading_is_below_the_budgets_start_is_not_remembered`, `…A_never_opening_message_is_remembered_at_the_budgets_end_only_if_its_code_started_within_the_start_allowance`).
- **R-10:** the stream learns per cycle in proportion to the lease.
- **R-11 (ours, not an owner decision):** a stream whose requests keep failing does not give up while pushes that bring something new, or accepted acknowledgements, keep coming before each give-up alarm fires.
  - Why: such a push or acknowledgement shows that the session is alive, so it lets the give-up alarm go. It does not restart the back-off (owner decisions B1 and F; I-18).
  - Who is affected: a recipient whose mediator still pushes but refuses or drops its requests. Its stream keeps retrying instead of ending.
  - Bound: its cycle requests stay at one per back-off, at most one per 30 s (the two `LiveStreamRt2CTests` measurements under I-18).
- **R-12 (ours, not an owner decision):** when a drain outlasts the mediator's lease, the messages it already reported come back first, and a round made only of them ends the drain (I-19).
  - Why: a Message Pickup 3.0 `delivery-request` has no offset, so the client cannot step past messages the mediator keeps returning first.
  - Who is affected: a recipient with more messages that are slow to open than one drain can pass within a lease. Messages queued behind those wait one more `LivePollInterval`.
  - Nothing is lost: live mode stays on, and unacknowledged messages stay queued.
- **R-13 (kept and restated; the coordinator's call; the red team's F4 folded in).** Its first form, in the docs of fix round 1, was about the moment right after a cut at a share; there are no cuts now.
  - A lookup that has been cancelled keeps its place until it ends. If the next delivery arrives before that, messages of the same sender (or, without a named sender, of that mailbox) beyond the places still free are refused at once and come again. Other senders' messages are not affected.
  - With a lookup that ends as soon as it is cancelled this is rare. With one that takes even a millisecond to end, and a delivery that follows immediately, it is the usual outcome.
  - Every bound for reaching a message is stated on the condition that the lookups of one delivery have ended when the next one starts. A delivery that starts earlier refuses, takes no time, and those messages wait for their next delivery, at most one lease.
  - The pins that show what happens without that condition:
    - `DeliveredUnpackNextDeliveryRt3Tests.While_the_lookups_of_the_delivery_before_are_still_ending_the_next_delivery_starts_what_the_bound_of_sixteen_leaves_free_and_refuses_the_rest` (sixteen still ending: all sixteen of the next are refused; ten: six start and four are refused; four: none is refused);
    - `SlowSenderFetchMatrixTests.A_fetch_that_arrives_while_the_lookups_of_the_fetch_before_are_still_ending_refuses_what_the_bound_does_not_leave_free_and_the_message_is_returned_a_lease_later` (returned at 80 s instead of 40 s).
  - A call that never got a thread keeps its place until the thread pool reaches its cancelled work item (the red team's F4). **Pending (2026-11-25):** its test is being un-skipped as a pin; it is cited here once merged.
  - The real-clock measurement behind the second bullet is table B, under "Fix round 3".
- **R-14 (now a pointer).** A message that starts later than the start allowance is not remembered at the budget's end: R-8 (a). In the docs of fix round 1 this residual carried a sentence labelled as the owner's wording. No literal owner text for it is on record, so that label is withdrawn.
- **R-15 (restated for S2; the coordinator's call).** An honest message whose code started within the start allowance and has not opened when the budget ends is remembered, also when a busy thread pool cost it part of that allowance. It is then held back for its pause.
- **R-16 Combined caller tokens (findings 3 and 3a of the red team on fix round 2; a documented residual by the coordinator's call).**
  - The client is handed one token. Host code (a resolver, a transport) that watches a different token than the one it is handed, and reports that token's cancellation as a failure, has that failure taken as the message's or the request's own.
  - Host code should watch the token it is handed.
  - Pins: `DeliveredUnpackTokenStateRt3Tests.A_failure_reported_from_one_of_two_combined_caller_tokens_is_the_messages_own_and_one_from_the_token_handed_ends_the_delivery_cancelled`, `MediatorClientChannelTokenStateRt3Tests.A_call_whose_token_is_combined_from_two_ends_with_what_its_host_code_reported_when_that_code_watches_one_of_the_two`.
- **Suspected by the red team on fix round 2, not demonstrated; no change (the coordinator's call; no id; in this plan only).** A call that opened just before the budget's end, and whose worker was not yet told, is recorded as out of time. An outcome not recorded when the budget ends is out of time; the message is tried again after its pause.
