## Problem

`UnpackAsync` verifies/decrypts with a JWK obtained from DID resolution **A**
(`DidKeyServiceLookups` → `GetVerificationMethodsAsync`), then authorizes the same kid via a
**second** resolution **B** (`IsKeyAuthorizedAsync` behind the FR-CONSIST-06 predicate). The
two documents can differ (rotation, cache eviction, replicas, hostile resolver), so the
library can assert an identity by combining facts never simultaneously true in any one
document. Evidence (exact key, controller, relationship) is discarded — consumers only get
kid strings + flags.

## Design (additive, binary-compatible)

1. **`ResolvedKeyBinding`** (public, `DidComm.Resolution`) — atomic projection from ONE
   resolved document: normalized absolute `Kid`, `Did` (subject of kid), `Controller`,
   `Relationship`, `PublicJwk`, `PublicKeyThumbprint` (RFC 7638 SHA-256 base64url via
   DataProofsDotnet.Jose `JwkThumbprint`).
2. **`IDidKeyBindingService`** (public capability interface) —
   `Task<ResolvedKeyBinding?> ResolveKeyBindingAsync(kid, relationship, ct)`. Implemented by
   `NetDidKeyService`: derive DID from kid, resolve once, match normalized kid under the
   relationship; **duplicate/shadowed matches ⇒ `DidResolutionException`** (fail closed);
   unusable curve / absent ⇒ null. Custom `IDidKeyService` impls are untouched (no
   capability ⇒ legacy path, no strong provenance).
3. **Per-unpack lookup context** (`UnpackKeyBindingContext`, internal) — created inside each
   `UnpackAsync`; serves the existing JOSE sender/signer lookup contracts; on the capability
   path each lookup resolves once, hands JOSE the exact JWK, and **captures the binding**
   keyed by (kid, relationship). No statics, no AsyncLocal, no TTL — instance dies with the
   call. Legacy path delegates to the existing `DidKeyServiceLookups` behavior.
4. **Same-binding authorization** (`EnvelopeReader` plaintext branch, capability path):
   - sender/signer: NO re-resolution. Validate `message.From`'s DID subject against the
     **captured** binding (id-subject + controller rule ⇒ `ConsistencyException` on
     mismatch, same exception class as today's FR-CONSIST-06).
   - recipient: resolve once, after the decrypting kid is known, via the capability;
     authorize against the same single document that produced the evidence.
   - Legacy path (no capability): existing resolverCheck behavior, bindings absent.
5. **`VerifiedKeyBinding`** (public, `DidComm.Facade`, internal ctor ⇒ unforgeable):
   `Kid`, `Did`, `Controller`, `Relationship`, `PublicKeyThumbprint`. Propagated:
   internal `Composition.UnpackResult` → public `UnpackResult` → `InboundMessageSnapshot`
   → `InboundObservation` as `SenderKeyBinding` / `SignerKeyBinding` / `RecipientKeyBinding`,
   all `{ get; internal init; }` (NO positional-ctor changes — binary compatible).
   `InboundMessageSnapshot.CreateFallback` and `InboundObservation.FromUnpackResult` on a
   non-registered message do **not** carry bindings (synthetic results can't manufacture
   provenance; `FromUnpackResult` uses the registered snapshot's bindings when the message
   identity is intact).
6. Version 1.4.0; `PackageValidationBaselineVersion` 1.3.0 (published); ApiCompat via
   `dotnet pack` must pass clean.

## Test matrix (mapped to issue acceptance criteria)

- Rotated key, same kid (signed + authcrypt): resolver serves doc A at crypto time then doc B —
  assert exactly ONE sender/signer resolution, binding thumbprint == KA, doc B never consulted.
  Inverse ordering (crypto sees B, envelope made with KA) ⇒ CryptoException.
- Key/controller splice across versions cannot yield Authenticated with mixed facts.
- Post-sign tampering + self-consistent forged docs still rejected (existing tests stay green).
- Concurrent unpacks, same kid: independent bindings, no cross-talk.
- Outbound pack / unrelated resolutions don't touch inbound evidence (per-call context).
- Fail-closed: relative ids, embedded methods, references, duplicate ids, missing controller,
  cross-DID controller, wrong relationship.
- anoncrypt(sign(...)) and nested shapes: correct per-role bindings, flags unchanged.
- Snapshots/observers carry bindings; synthetic fallback yields none.
- Legacy IDidKeyService: source/binary compatible, no bindings, old checks still run.
- ApiCompat vs 1.3.0 clean.
