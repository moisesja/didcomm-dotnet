## Problem

`UnpackAsync` verifies/decrypts with a JWK obtained from DID resolution **A**
(`DidKeyServiceLookups` → `GetVerificationMethodsAsync`), then authorizes the same kid via a
**second** resolution **B** (`IsKeyAuthorizedAsync` behind the FR-CONSIST-06 predicate). The
two documents can differ (rotation, cache eviction, replicas, hostile resolver), so the
library can assert an identity by combining facts never simultaneously true in any one
document. Evidence (exact key, controller, relationship) is discarded — consumers only get
kid strings + flags.

## Design (additive, binary-compatible)

1. **`ResolvedKeyBinding`** (public, `DidComm.Resolution`) — atomic projection from ONE
   resolved document: normalized absolute `Kid`, `Did` (subject of kid), `Controller`,
   `Relationship`, `PublicJwk`, `PublicKeyThumbprint` (RFC 7638 SHA-256 base64url via
   DataProofsDotnet.Jose `JwkThumbprint`).
2. **`IDidKeyBindingService`** (public capability interface) —
   `Task<ResolvedKeyBinding?> ResolveKeyBindingAsync(kid, relationship, ct)`. Implemented by
   `NetDidKeyService`: derive DID from kid, resolve once, match normalized kid under the
   relationship; **duplicate/shadowed matches ⇒ `DidResolutionException`** (fail closed);
   unusable curve / absent ⇒ null. Custom `IDidKeyService` impls are untouched (no
   capability ⇒ legacy path, no strong provenance).
3. **Per-unpack lookup context** (`UnpackKeyBindingContext`, internal) — created inside each
   `UnpackAsync`; serves the existing JOSE sender/signer lookup contracts; on the capability
   path each lookup resolves once, hands JOSE the exact JWK, and **captures the binding**
   keyed by (kid, relationship). No statics, no AsyncLocal, no TTL — instance dies with the
   call. Legacy path delegates to the existing `DidKeyServiceLookups` behavior.
4. **Same-binding authorization** (`EnvelopeReader` plaintext branch, capability path):
   - sender/signer: NO re-resolution. Validate `message.From`'s DID subject against the
     **captured** binding (id-subject + controller rule ⇒ `ConsistencyException` on
     mismatch, same exception class as today's FR-CONSIST-06).
   - recipient: resolve once, after the decrypting kid is known, via the capability;
     authorize against the same single document that produced the evidence.
   - Legacy path (no capability): existing resolverCheck behavior, bindings absent.
5. **`VerifiedKeyBinding`** (public, `DidComm.Facade`, internal ctor ⇒ unforgeable):
   `Kid`, `Did`, `Controller`, `Relationship`, `PublicKeyThumbprint`. Propagated:
   internal `Composition.UnpackResult` → public `UnpackResult` → `InboundMessageSnapshot`
   → `InboundObservation` as `SenderKeyBinding` / `SignerKeyBinding` / `RecipientKeyBinding`,
   all `{ get; internal init; }` (NO positional-ctor changes — binary compatible).
   `InboundMessageSnapshot.CreateFallback` and `InboundObservation.FromUnpackResult` on a
   non-registered message do **not** carry bindings (synthetic results can't manufacture
   provenance; `FromUnpackResult` uses the registered snapshot's bindings when the message
   identity is intact).
6. Version 1.4.0; `PackageValidationBaselineVersion` 1.3.0 (published); ApiCompat via
   `dotnet pack` must pass clean.

## Test matrix (mapped to issue acceptance criteria)

- Rotated key, same kid (signed + authcrypt): resolver serves doc A at crypto time then doc B —
  assert exactly ONE sender/signer resolution, binding thumbprint == KA, doc B never consulted.
  Inverse ordering (crypto sees B, envelope made with KA) ⇒ CryptoException.
- Key/controller splice across versions cannot yield Authenticated with mixed facts.
- Post-sign tampering + self-consistent forged docs still rejected (existing tests stay green).
- Concurrent unpacks, same kid: independent bindings, no cross-talk.
- Outbound pack / unrelated resolutions don't touch inbound evidence (per-call context).
- Fail-closed: relative ids, embedded methods, references, duplicate ids, missing controller,
  cross-DID controller, wrong relationship.
- anoncrypt(sign(...)) and nested shapes: correct per-role bindings, flags unchanged.
- Snapshots/observers carry bindings; synthetic fallback yields none.
- Legacy IDidKeyService: source/binary compatible, no bindings, old checks still run.
- ApiCompat vs 1.3.0 clean.

## Review

### Delivered

All checklist items complete. `feat/same-doc-key-provenance-56`, 1.4.0, ApiCompat clean vs the
published 1.3.0 baseline, 802 tests green (643 core + 159 interop; 45 new).

Shape of the fix as built:

- `ResolvedKeyBinding` + `IDidKeyBindingService` (capability), implemented by `NetDidKeyService`
  in one `ResolveAsync` with duplicate/shadowed-kid rejection.
- `UnpackKeyBindingContext` per `UnpackAsync`: serves the JOSE sender/signer lookups, memoizes per
  (kid, relationship), returns the winner's binding on a race so the key handed to crypto is
  always the key in the captured evidence.
- `EnvelopeReader` authorizes sender/signer against captured evidence (no re-resolution), resolves
  recipient evidence once post-decrypt, and attaches `VerifiedKeyBinding` to result + snapshot +
  observation. Legacy path (no capability) unchanged.

### Adversarial review outcomes

A dedicated adversarial subagent attacked the diff. Two substantive findings were fixed in the
same branch, and the review earned its cost:

1. **`from_prior` had the identical TOCTOU** inside the same `UnpackAsync` — authorize in one
   resolution, verify with a key from a second. Worse payoff than the reported bug (forged
   accepted rotation ⇒ inherit the prior DID's relationships). Fixed in `FromPriorValidator`
   with the same single-resolution + controller-rule shape; 5 tests.
2. **`RecipientKeyBinding` described a key that never decrypted.** The parser reports the label of
   whichever recipient entry the KEK opened, and labels are attacker-permutable (`apv` covers only
   the sorted kid list). Added the FR-CONSIST-08 fail-closed check that the reported recipient kid
   is the kid whose key agreement produced the KEK; proved the test fails without the check.

Contract issues also addressed: `AuthorizedForDid` (distinguishes "authorized against an asserted
identity" from "key evidence only" when `from` is absent), value equality on `VerifiedKeyBinding`
(otherwise `UnpackResult` record equality silently changed for 1.3.0 consumers), and explicit docs
that adopting the capability replaces `IsKeyAuthorizedAsync` during unpack, that decorators must
forward the interface, that two bindings on one result are separate resolutions, and that a record
`with`-copy carries evidence onto a message the pipeline never verified.

Confirmed clean by the same review (with stated evidence): sender/signer kid-confusion via the
DataProofs parsers, memoization divergence, JWK mutation between capture and use, controller-rule
divergence from `IsControlledBy`, lock/sync-over-async hazards, and dropped checks vs 1.3.0.

### Second adversarial pass (over the review-round fixes)

No authorization bypass; six Low-or-below findings, all resolved:

- Recipient selection iterated `FindPresentAsync`'s order while the parser scans envelope order —
  for an envelope with the same key material under two kids that could **false-reject a legitimate
  message**. Now selects in envelope order (proved: the new theory fails with the old selection).
- The "reveals nothing about which recipient keys are held" comment on the label check was wrong —
  reaching that throw does mean our key opened an entry. Corrected to the accurate claim: it is not
  a *new* distinguisher (decrypt success already is one), so the constant-work guarantee stands.
- `from_prior` `iss` was no longer required to be a bare DID (subject-wise comparison), letting a
  prior-key holder mint equivalent-but-distinct `iss` values against an app's replay state. Now
  rejected.
- A rejected envelope tore down a WebSocket connection (only Malformed/Crypto were caught).
  Pre-existing; my change widened reachability, so fixed here: any `DidCommException` is dropped.
- `AuthorizedForDid` stored `from` verbatim for sender/signer (subject for recipient) — normalized.
  Note: the facade already refuses a decorated `from` at every perimeter, so the reviewer's
  attacker scenario was unreachable; the test now pins that perimeter instead of the unreachable
  path (the first attempt at that test failed, which is how the perimeter behavior surfaced).
- Wrong FR id in a thrown message (FR-CONSIST-02 → 08) and missing `==`/`!=` on the binding type.

The kid/iss pre-resolution guard that the pass listed as F4 had already been fixed (`ec3ccd9`).

### Deliberate non-goals / follow-ups

- No `DidCommOptions` strict mode requiring provenance (would be new config surface; documented
  instead). Candidate for a follow-up if consumers ask.
- No binding surfaced for the `from_prior` signer (the TOCTOU is fixed; exposing a fourth public
  evidence property was left out to keep the 1.4.0 surface tight).
- Upstream/pre-existing, out of scope here: a non-string JWS `header.kid` can surface a raw
  `InvalidOperationException` from the DataProofs JWS parser, escaping the FR-API-07 contract
  (the JWE branch has a catch-all; the JWS branch does not). Worth its own issue.
