## Item A — null-safe dispatcher catch handler

**File:** [src/DidComm.Core/Protocols/ProtocolDispatcher.cs:140](src/DidComm.Core/Protocols/ProtocolDispatcher.cs#L140)

The `catch` that isolates snapshot failure logs `received.Message.Id` — the very expression whose
null-ness can *be* the fault it is handling (`TryGetFor`/`CreateFallback` both
`ArgumentNullException.ThrowIfNull(message)`). With an observer or correlator registered,
`DispatchAsync(new UnpackResult(Message: null!, …))` therefore escapes as `NullReferenceException`
thrown *from inside the catch*; with neither registered the same input produces a clean
`ArgumentNullException` (from `AckLoopGuard.IsPureAck`, verified: `AckLoopGuard.cs:36`).

- [ ] A1. `received.Message.Id` → `received.Message?.Id` in the catch at line 140.
- [ ] A2. Leave line 176 (`Observer enqueue threw …`) as a plain dereference. It is provably
  non-null: it only runs when `snapshot is not null`, and both paths that assign `snapshot`
  null-check `received.Message` first. No speculative `?.` where the invariant already holds.
- [ ] A3. Do **not** add an up-front `ArgumentNullException.ThrowIfNull(received.Message)`.
  Considered and rejected: it changes the surfaced `paramName` on an input the library never
  produces, for no gain — with A1 in place both configurations already converge on the same clean
  `ArgumentNullException`.

**Tests** (new, deterministic — this also serves as the pin for the dispatcher's snapshot guard):

- [ ] A4. `DispatchAsync_NullMessage_WithObserverRegistered_FaultsAsArgumentNullException` — the
  regression test for this fix. Fails with `NullReferenceException` on today's code.
- [ ] A5. `DispatchAsync_NullMessage_WithoutObservers_FaultsAsArgumentNullException` — pins the
  parity baseline, so a future change to either path can't drift them apart silently.
- Location: `tests/DidComm.Core.Tests/Protocols/Dispatch/ProtocolDispatcherObserverTests.cs`
  (reuses that file's existing dispatcher/observer construction helpers).

## Item B — document `FromUnpackResult`'s caller-owned thread affinity

**File:** [src/DidComm.Core/Protocols/InboundObservation.cs:113](src/DidComm.Core/Protocols/InboundObservation.cs#L113)

The public compat helper serializes the caller's **live** `Message`. A `To`/`Ack` list mutated on
another thread during that serialize makes `JsonSerializer.Serialize` throw
`InvalidOperationException` (collection modified during enumeration). The library's own receive path
is unaffected — observer delivery materializes from the immutable snapshot via `FromSnapshot`, and
the one receive-path site that serializes a live message (`CreateFallback`) sits inside the
dispatcher's guarded `try`. What is wrong today is only that the public API surfaces an undocumented
exception.

- [ ] B1. Add `<exception cref="ArgumentNullException">` (null `received`) and
  `<exception cref="InvalidOperationException">` (caller mutated `received.Message` — typically its
  `To` or `Ack` list — on another thread during the call) to the public
  `FromUnpackResult(UnpackResult)`.
- [ ] B2. Add a one-paragraph `<remarks>`: thread affinity is the caller's; the message must not be
  mutated concurrently with this call. Note that library-internal delivery never hits this class of
  fault because it reads the immutable snapshot, so this is a contract note for the compat path only.
- [ ] B3. Mirror a single sentence on the `internal` overload at line 123 (where the serialize
  actually happens), so the next reader doesn't have to re-derive the constraint.
- No test: a test for B would have to *win* a race to assert anything, and would only ever be
  flaky-green. The deterministic half of this seam (the dispatcher's guard around the live-message
  serialize) is pinned by A4/A5 instead.

## Item C — regression tests: exactly one snapshot registration per unpack

Today `EnvelopeReader.UnpackAsync` has the single repo-wide `RegisterVerified` call site
(`EnvelopeReader.cs:272`). The hazard the issue names is a *future second* call site turning
`ConditionalWeakTable.Add`'s duplicate-key `ArgumentException` into a remote unpack fault. The tests
below make that failure loud and diagnosable in CI instead of surfacing as an unrelated test's
mystery throw.

**New file:** `tests/DidComm.Core.Tests/Facade/SnapshotRegistrationTests.cs` (self-contained
pack/unpack harness modeled on `SameDocumentProvenanceTests`' private helpers — resolver, `Doc`/`Auth`/`Ka`
builders, `Client`; reuses the shared internal `TestKeyMaterial` / `DictionarySecretsLookup`).

- [ ] C1. `Unpack_RegistersExactlyOneCoveringSnapshot` `[Theory]` over every envelope shape:
  plaintext, signed, anoncrypt, authcrypt, and signed-then-anoncrypt (the legal nesting). For each:
  unpack completes (a duplicate `Add` would throw here), `TryGetFor(result.Message)` is true, and the
  snapshot's `PlaintextJson` round-trips to the same content as the returned message.
- [ ] C2. `Unpack_EnvelopeShapedPayloads_RegisterOnlyTheOuterMessage` — the attacker-shaped nesting
  probes from the re-verification: an inner JWM in `body`, a JWE/JWS-shaped `body`, an
  attachment-borne JWM, and a JWM in an extension header. Each must register exactly once, for the
  **outer** message id.
- [ ] C3. `RepeatedUnpacks_OfIdenticalBytes_EachGetTheirOwnSnapshot` — 50 sequential + 64 parallel
  unpacks of byte-identical input: every returned `Message` reference-distinct, every one covered by
  its own snapshot, zero faults. A CI-sized net under the 4500-run manual probe.
- [ ] C4. `RegisterVerified_Twice_ForTheSameMessage_ThrowsFailFast` (unit, appended to
  `tests/DidComm.Core.Tests/Protocols/Dispatch/InboundMessageSnapshotTests.cs`) — the positive
  control. Proves C1–C3 are not vacuous (the probe *can* catch a duplicate) and pins the deliberate
  choice of `Add` over `AddOrUpdate`, with the reason in the assertion message.

### C5 — DROPPED by the user. See the review section: the gap it covered is closed by C1–C3's counting method.

<details>
<summary>Original proposal (not implemented)</summary>

- [ ] C5. `RegisterVerified_HasExactlyOneCallSiteInSrc` — walk up from `AppContext.BaseDirectory` to
  the repo root (marker: `DidComm.sln`), enumerate `src/**/*.cs` excluding `bin`/`obj`, assert
  exactly one call site outside the declaring file, with a failure message that explains the rule and
  cites #63.

  **Why include it:** C1–C4 only catch a second call site that registers the *same* `Message`
  instance. A second site registering a *different* instance (e.g. a future forward/routing path
  registering an inner message) violates "one registration per unpack" and would pass C1–C4 silently
  while re-arming the duplicate hazard for later. C5 is the only check that literally makes *any*
  future call site fail loudly in CI — the issue's stated goal.

  **Cost:** introduces a source-scanning test pattern this repo does not yet have, and fails if the
  test binary is ever run detached from the source tree (CI is not). Say the word and I drop it —
  C1–C4 stand on their own.

### Two deviations from the approved plan

1. **A2 reversed — line 182 also takes `?.`.** The plan said to leave the observer-enqueue catch's
   `received.Message.Id` alone because it is provably non-null (it only runs when `snapshot is not
   null`, which implies a non-null message). The compiler disagreed: once the first site reads
   `received.Message?.`, nullable flow analysis marks the property maybe-null for the rest of the
   method, and the build failed with `CS8602` at that second site. Arguing with the analyzer via `!`
   inside an isolation boundary is the wrong trade, so both logging sites are now null-conditional —
   same behavior, and no logging site in the method can raise a second fault while handling the first.
2. **C1–C3 count registrations instead of just observing "no throw".** The plan's design would only
   have detected a second registration against the *same* message instance (the `Add` that throws).
   The implemented tests embed a per-test marker in the plaintext and count matching entries in the
   weak table by reflection, which also detects a second registration against a *different* instance
   — the silent case, and precisely the gap C5 was proposed to cover. Verified by mutation, below.

### Mutation testing — every new test proven to fail on the defect it pins

| Mutation | Expected | Observed |
| --- | --- | --- |
| `received.Message?.Id` → `.Id` | both parity tests fail | **2 failed**, `Expected ArgumentNullException … found NullReferenceException` |
| second `RegisterVerified` in `EnvelopeReader`, **same** instance | registration tests fail | **12 of 12 failed** |
| second `RegisterVerified` in `EnvelopeReader`, **different** instance (silent — `Add` accepts it) | registration tests fail | **12 of 12 failed** |

Both mutated files were byte-compared against pre-mutation backups after restore (`diff` clean).

The third row is the load-bearing result: it is the case a "did unpack throw?" test cannot see, and
it is why dropping C5 costs no coverage. C5's only remaining advantage would have been catching a
second call site that never executes under test — a case with no runtime consequence.
