# Issue #72 — Transport retry classification: plain OCE + connect-time SSRF guard

Branch: `feat/issue-72-retry-classification` (off `main`). One PR, closes #72.
Scope: `src/DidComm.Transports.WebSocket/WebSocketDidCommTransport.cs` + its behavior
tests. No public API changes; every new type stays a private nested class.

## Risk verdict

**Not too risky — moderate and well-contained.** Both fixes reuse patterns that already
exist in this file (the `FatalHandshakeException` fatal-classification lane, and the
caller-vs-timeout distinction the catch-filter at `SendAsync` already draws). The two
real risks, each with a mitigation baked into the plan:

1. **Over-retrying (fix a):** naively adding `OperationCanceledException` to the retry
   list would make *caller* cancellation burn the backoff budget before propagating.
   Mitigation: the predicate consults `args.Context.CancellationToken` (Polly carries the
   token passed to `ExecuteAsync`) — a cancelled caller token is never retried. Tested
   both ways.
2. **Over-fataling (fix b):** pattern-matching connect failures too broadly would turn a
   transient DNS hiccup into a permanent refusal. Mitigation: mark the refusal **at the
   throw site** (wrap the guard's `TransportException` inside the `ConnectCallback` in a
   private marker type) and unwrap the `WebSocketException → HttpRequestException → marker`
   chain after `ClientWebSocket.ConnectAsync`. Only the marker is fatal; everything else
   keeps today's classification. `OutboundEndpointGuard` itself is untouched (shared with
   the HTTP transport — zero blast radius there).

## Phase 1 — Fix (a): plain `OperationCanceledException` is retryable when not caller-initiated

- [ ] In `BuildReconnectPipeline`'s `ShouldHandle` (`:517-524`): replace the
      `TaskCanceledException` arm with an `OperationCanceledException` arm (covers the
      subclass) guarded by `!args.Context.CancellationToken.IsCancellationRequested`.
      Keep `!_disposed` first. Net behavior: send-timeout OCE from a half-dead
      production socket → retried; caller cancellation → fatal, propagates as today via
      the `:257` catch-filter.
- [ ] Update the predicate's comment block to state the caller/timeout distinction and
      why it mirrors the catch-filter.

## Phase 2 — Fix (b): connect-time SSRF refusal fails fast instead of burning ~31 s of backoff

Defaults make this concrete: 5 attempts × exponential 1 s→30 s ≈ 31 s (jittered) holding
the endpoint's send gate, head-of-line-blocking every other sender to that endpoint.

- [ ] In the constructor's `ConnectCallback`: catch `TransportException` from
      `_guard.ConnectAsync` and rethrow wrapped in a new private marker
      `GuardRefusalException` (plain `Exception` subclass, carries the guard's
      `TransportException` as `InnerException`). `SocketException`/timeouts keep flowing
      untouched (still transient).
- [ ] In `DefaultConnect` (or a small wrapper around the `cws.ConnectAsync` call): catch
      `WebSocketException`, walk the `InnerException` chain; if a `GuardRefusalException`
      is found, throw the fatal wrapper carrying the guard's original `TransportException`.
      Otherwise rethrow unchanged.
- [ ] Generalize the private `FatalHandshakeException` into `FatalSendException` (rename
      of a private type — safe), used by both the STOMP version mismatch and the guard
      refusal. It carries the classified `TransportException` and a short reason string.
- [ ] Rework `SendAsync`'s fatal catch (`:262-273`) to build its message from the reason +
      the real attempt count — this also fixes the "no reconnect was attempted" lie on
      attempt 2+ (nit 3). Guard refusals surface the guard's own message via
      `InnerException`, same shape the STOMP fatal already has.

## Phase 3 — Batched nits (same file)

- [ ] **ODE race:** add `catch (ObjectDisposedException) { throw; }` before `SendAsync`'s
      catch-all so a send that passes the entry check but loses the race to dispose
      surfaces `ObjectDisposedException`, not "exhausted the reconnect budget".
- [ ] **Lifecycle deadlock doc:** XML-doc warning on the `Lifecycle` event: a handler
      that blocks synchronously on `DisposeAsync().GetAwaiter().GetResult()` deadlocks
      permanently (dispose-once latch waits on `_disposeCompleted`, which that handler is
      blocking). Doc only — a runtime guard can't distinguish this reliably.
- [ ] **PoolKey query string** (decision — recommend fixing): include `endpoint.Query` in
      `PoolKey`. Two endpoints differing only in query today share the socket whose
      handshake used the *first* sender's full URL — query strings routinely carry
      routing/auth material, so sharing is wrong. Pre-existing on `main`, not from #69;
      cost is at most more sockets. **Veto here if sharing was intentional.**
