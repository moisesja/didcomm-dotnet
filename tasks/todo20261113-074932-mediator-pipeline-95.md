### Judgement calls

- JC-1. **The delay cap lives where the draw is: Core.** `ForwardProcessor.ExtractDelay(message, maxDelay)` clamps `|n|` to the cap before `RandomNumberGenerator.GetInt32`, and a positive hint to `min(n, cap)`; the handler and the public `ProcessAsync` overloads both reach it through the processor's options. `AddMediator()` sets `MaxDelay` from `MediatorOptions.MaxForwardDelay`. A sink-side re-draw was rejected (two draws, a reconstructed receipt time, and a point mass at the cap if clamped after the draw).
- JC-2. **The age limit is folded into the record's `ExpiresAt` at admission**: `ExpiresAt = min(forward expiry (ExpiresClockSkew), ReceivedAt + MaxMessageAge)` on the mediator's clock, saturating near `MaxValue`. Every existing expiry path (lazy sweep, store-full sweep, `PurgeExpiredAsync`, lease selection, `status`) then applies it unchanged, to queued, leased and passed-over records alike, on time only (L-056). The `IMessageStore` contract change is a widening of what `QueuedMessage.ExpiresAt` means; no signature changes, and custom stores need no code change. Consequence (documented): the limit in force at admission is fixed on the record; lowering it later does not shorten records a persistent store already holds. `MaxMessageAge` lives on `MessagePickupOptions` because it binds every `DeliverAsync` caller, not only the pipeline. `MediatorOptions.Validate` refuses `MaxMessageAge <= MaxForwardDelay` (a delayed message would age out before it is due).
- JC-3. **Random ids**: 16 bytes from `RandomNumberGenerator` as 32 lowercase hex characters (unreserved, within `PickupSizing.MaxMintedIdLength`). The container's `IMessageIdGenerator` is no longer read; tests that injected one use an internal `PickupIdSource` seam that only InternalsVisibleTo code can register.
- JC-4. **Queue first, then direct push, detached and bounded.** The record is admitted under quota before any push, so a crash mid-push loses nothing and pushes are bounded by admission. Inline on `ForwardHandler`'s single pump one tarpitting endpoint would stall every relay and then drop forwards for everyone (L-059), so pushes run on `DirectPushConcurrency` workers with a 1024-job / 64 MiB / 16-per-grant backlog; saturation → skipped, the message stays queued. A push re-checks the registration first, uses a guarded timer (never `CancelAfter` on a token host code sees), and counts only an HTTP 2xx (`Accepted` with a 2xx status) as delivery → `RemoveAsync`. **ws(s) targets are not pushed**: the WebSocket transport reports `Accepted` when the frame is written, with no receipt, so counting it would turn a dropped connection into silent loss; recipients that want push over a socket use pickup live mode, which is acknowledged. A not-yet-due message is not pushed. One attempt per message: a failure leaves it queued for pickup — the issue's "treat a transport failure as queue instead"; a push-only recipient must also pick up (documented limit; a retry drain is a follow-up candidate, not #95 scope).
- JC-5. **The egress target never comes from the message**, only from the host's `IRecipientEndpointDirectory`, called only on push workers (never on the request or the pump); a throw means "skip". `DidCommClient` and the directory are resolved lazily on the first push (L-017; no cycle through the facade, router or transports; nothing built when push is off).
- JC-6. **Post-enqueue re-check (L-057).** A forward admitted before `RevokeAndPurgeAsync` can store a record after the purge; `DeliverAsync` looks the recipient up again after `EnqueueAsync` and, if the grant no longer owns the DID, removes exactly the record it stored (by id) and reports `NotRegistered`. If the re-check faults the record is kept (never lose; expiry or the age limit reclaims it).
- JC-7. **Per-grant extra routing keys need no new type.** CM 3.0 has no wire message to register routing keys; the per-recipient `IRecipientRoutingKeyProvider` seam (#90) is it — a host registers its provider before `AddMediator()`. `RewrapMode.ReanoncryptToNext` together with a host provider is refused at registration (it would be silently ignored).
- JC-8. **Options composition by projection.** One `Action<MediatorOptions>` reaches each role's `IOptions<T>` through a view whose slot for `T` is the instance being configured, so the delegate assigns only what the host sets and composes with a host's own `Configure<T>` by registration order (whole-object copies would clobber earlier host settings). The delegate may run several times and must only assign values. Validated on a probe at registration, by each role at construction, and all together at startup.
- JC-9. **Startup is `IHostedLifecycleService.StartingAsync`** (runs before Kestrel listens): identity (≥ 1 bare routing DID, also for a host's own `IMediatorIdentity`), the sink in effect is the mediator's, resolve the dispatcher (builds every handler: `MessagePickupQueue` validates `MaxDeliveryBytes` and logs the admissible size; `ForwardProcessor` validates `MaxDelay`), resolve the replay guard and session registry (bad settings fail at startup), FR-MED-07 per routing DID (first `DIDCommMessaging` entry, absolute `http(s)`/`ws(s)` uri, not a DID or the queue URI; at least one keyAgreement key whose secret is held; routing keys on the mediator's own entry → Warning; resolution failure or timeout fails startup — senders resolve the same DID, so it would be unreachable anyway), build the OOB invitation, one Information line with no DID. `StartedAsync` starts the purge loop (`PeriodicTimer` on an injectable `TimeProvider`; `PurgeOnceAsync` is the test seam; it also reports deltas of `SaturationCount`, `ClockBehindRefusalCount`, `DroppedNotifications` as Warnings). Outside a generic host nothing starts and the checks run lazily at first use (documented).
- JC-10. **`MapDidCommMediator(pattern)`**: `POST {pattern}` = the public registry-aware `MapDidCommEndpoint(pattern)`, unchanged; `GET {pattern}` = the WebSocket core with same-socket replies forced on and STOMP off (STOMP sessions can never push, so pickup over it would be silent) for this endpoint only — the host's other WebSocket endpoints keep FR-TRN-10 one-way; `GET {base}/oob` = `MapDidCommOobEndpoint` over a read-only store that serves the mediator's invitation (`from` = the first routing DID, `goal_code: "request-mediate"`, `accept: ["didcomm/v2"]`, the Identus/Blocktrust shape) under the fixed id `InvitationOobId = "mediator"`. A composite convention builder applies `.RequireRateLimiting(...)` etc. to all three. Without `AddMediator()` it throws at map time. InternalsVisibleTo rather than a public `DidComm.AspNetCore` overload: no public surface on a released package for one caller; all packages ship in lockstep from one `DidCommVersion`.
- JC-11. **Observability in Core and Mediator.** Meter `didcomm-dotnet`: `didcomm.forward.outcomes` (tag `didcomm.forward.outcome`; one outcome per forward from whichever stage ended it: handler `Dropped-Malformed`, `Dropped-NotEncrypted`, `Dropped-Expired`, `Dropped-Unknown`, `Dropped-Saturated`, `Dropped-Unacknowledged`, `Dropped-Shutdown`, `Faulted`; sink `Delivered-Live`, `Queued`, `Dropped-Unknown`, `Dropped-Expired`, `Dropped-TooLarge`, `Dropped-Quota`, `Faulted`), `didcomm.mediator.direct_push.outcomes` (`Pushed`, `Push-Failed`, `Push-Skipped-*`), `didcomm.mediator.queue.purged`, observable replay / session / queue gauges for the in-memory types. The counter must be in Core because most `Dropped-Expired` / `Dropped-Unknown` happen in the handler (L-052). Logs: message id via `LogId`, exception type names only, no DID / record id / endpoint at any level; drop lines rate-limited per reason (first and every 1000th at Warning, else Debug) — including `ForwardHandler`'s per-forward drop Warnings, which a stranger can flood.
- JC-12. **One PR.** The architect suggested two sequential PRs (forward core + queue hardening, then the service). I keep one: every piece is #95 scope, the commits are ordered so each is reviewable alone, and #94 (PR #107) was of the same size. Recorded so the reviewer can ask for a split.

## Threat model (L-031)

- **Registration surface.** Host code at startup registers the directory, stores, policy, identity and routing-key provider (TryAdd, before `AddMediator()`); a foreign `IForwardSink` or an earlier `AddRoutingMediator()` is refused at registration, a sink registered later at startup. In-process host code is trusted; its boundary is that the directory runs only off the request path and the pump, its faults are logged by type and mean "skip".
- **Who can call what.** Anyone reaching the endpoint can post forwards (relayed only for a registered `next`) and fetch the OOB invitation (public routing DID only). Only authcrypt peers that pass replay admission enrol or pick up (#93/#94, unchanged). `RevokeAndPurgeAsync`, `PurgeExpiredAsync` are host APIs.
- **Quota exhaustion.** Delays: bounded by the cap (residual, owner-accepted: unseen occupation for at most the cap after the sender stops). Ids: 128-bit random, unpredictable, host generators unreachable. Age limit: only removes (residual, owner-accepted: silent loss after 30 days offline). Store-wide bounds via self-made grants: allow-list / rate-limit policy guidance (residual: availability for everyone, as W-2).
- **Sink / direct push as amplifier or SSRF lever.** Target only from the host directory; `SendPackedAsync` always applies the SSRF guard (plus connect-time pinning in the HTTP transport); only stored records are pushed, 1:1, after the 202 and off the pump; concurrency, backlog, bytes and per-grant pending bounded; per-push guarded timeout; saturation = stays queued. Residuals: the HTTP transport's own retries; its circuit breaker can be opened by a failing recipient endpoint and pause the mediator's push egress (messages stay queued); anyone can make the mediator relay up to `MaxAdmissiblePayloadBytes` to a registered recipient's push endpoint (as they could post there directly); a directory pointing at the mediator itself allows bounded onion re-entry (misconfiguration).
- **Timing oracles on `next`.** The 202 is committed before the processor and sink run; the inline lookup is constant-work; the inline difference is a reservation versus a rate-limited log line; measured over HTTP (ratio < 3, the FR-MED-08 gate). Direct push and the re-check run after the 202.
- **Log injection.** Ids are unreserved URI characters at unpack and capped by `LogId`; structured templates only; no DID, endpoint or exception text; checked with the existing leaking-log-line helpers.
- **DI lifetimes and cycles.** All singletons; the sink, dispatcher and metrics take no registry, dispatcher, handler or `DidCommClient` at construction; `DidCommClient` and the directory are resolved on push workers; the hosted service resolves in `StartingAsync`, not its constructor; the queue factory is already cycle-guarded; the `ForwardHandler` factory keeps `DependencyCycleGuard` coverage.
- **The new package's composition.** Three routes, same-socket replies scoped to the mediator socket, STOMP off on it, sessions only for authcrypt + `return_route: all` + admitted messages (#91 rules, unchanged), real acknowledgement on HTTP, admission on both.
- **Revocation race.** Closed for the pipeline by JC-6. Residuals: deliveries already in flight; a peer granted again during the call loses records stored for the new grant before the purge (deny it in the policy before revoking).
- **Clock.** Aging is judged by each caller's reading; a request read just before a sweep can still deliver a just-aged record (reading skew only, never resurrection: removal is by the lock holder; L-060). Settings are copied at construction everywhere.
