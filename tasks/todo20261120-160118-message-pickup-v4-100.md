### Readings (checked against the text; none is a stop)

- **R-1. `delivery.thid`.** L263 read alone is ambiguous; L34 says why it became optional (live deliveries answer no request), and v2.1 threading L17 / problems L55 require `thid` on every later message of a thread. So a `delivery` that answers a `delivery-request` carries `thid`, a live one has none. The client keeps owner answer "2" (#98): a reply without `thid` completes no request; a thread-less `delivery` is only ever a live push.
- **R-2. No on-time push (owner decision D2, 2026-11-14, #88 comment 6881144022, item 2: "No scheduler for due messages (option A)… For #100: if Pickup 4.0's live-mode text turns out to require pushing a message when it becomes due, raise it as an owner decision then.").** 4.0 L85 = 3.0 L63 + "via a `delivery` message"; L302–L306 = 3.0 L201–L205 (3.0's lower-case "must" in L203 is MUST in L304); L308 is new and requires `delivery` + `messages-received` and re-queueing, with no time bound. Nothing about due times: D2 stands.
- **R-3. Thread placeholders.** "<message id of status-request message>" (L149), "<message id of delivery-request message>" (L241) are the common case of DD-11 (request `thid` ?? `id`, v2.1 L15/L17). Answer threads come from `MessagePickup.ResponseThreadId`.
- **R-4. `return_route`.** L35 removes it from `messages-received`; L69 asks for it on "all request", and L59–L63 list three requests, of which `messages-received` is not one. On a WebSocket a header-less message leaves the session unchanged (FR-RR-05); over HTTP it is answered 202. No reply is ever sent to a 4.0 `messages-received`.
- **R-5. `message_count_limit`.** L206/L255 say what 3.0's `limit` said, made stricter (MUST NOT exceed). 3.0's reading rules apply: REQUIRED, 0 valid (→ empty `delivery`), negative / non-zero fraction / non-number malformed, huge values clamped then capped by `MaxDeliveryBatch` (never above the request). A body that has only 3.0's `limit` is malformed (no fallback, L-074).
- **R-6. Empty `delivery`.** L210 "no messages are available to be sent" covers what the coordinator already reports as "nothing deliverable now" (L-056: empty, passed over, all leased, limit 0). Written as `"attachments": []` (L259).

## Design calls (architect pass reconciled; each has a reason; all are ours unless marked "owner")

- **DC-1. Internal 4.0 codec `MessagePickup40`** (`src/DidComm.Mediator.Client/Pickup/MessagePickup40.cs`, namespace `DidComm.Mediator.Pickup`), both directions, after the `CoordinateMediation20` precedent: type URIs (any 4.x matches, canonical strings written), builders, strict parsers, the 4.0 problem report (a `MessageBuilder` message of type `…/message-pickup/4.0/problem-report`, `pthid`, body `{code, comment}`; Core's `ProblemReport.Create` hard-codes `report-problem/2.0`). Internal record `PickupStatus40` (ms). An empty delivery gets `Attachments = []` after `Build()` (the builder creates the list lazily; `DidCommJson` writes an empty list). Reason: only the 4.0 handler and `PickupClient` use it; no public message API to demonstrate; reached by the existing `DidComm.Mediator.Client` → `DidComm.Mediator` IVT grant (no new grant, `ShippedAssembliesListTests` unchanged).
- **DC-2. Public `PickupStatus` keeps epoch seconds.** The client maps 4.0's milliseconds to seconds (floor); `LongestWaitedSeconds` is null under 4.0. Nothing public changes; the record's docs say so. The mediator never goes through `PickupStatus` for 4.0 (it writes `PickupStatus40` from the coordinator's view), so the wire keeps exact milliseconds. Rejected: changing the record's member types (churn in the public 3.0 codec and its fixtures for an informational field).
- **DC-3. `MessagePickup40Handler`** (public, sealed, `IProtocolHandler, IProtocolHandlerRoles`, same constructor shape as `MessagePickupHandler`), thin over `queue.Coordinator`: status-request → `StatusAsync` → 4.0 `status`; delivery-request → `DeliverRequestedAsync` with the 4.0 builder, "status" outcome → empty 4.0 `delivery` (`thid`, filter echo); messages-received → `AcknowledgeAsync(answerWithStatus: false)` → null; live-delivery-change → `SetLiveDeliveryAsync` with the 4.0 live framing → 4.0 `status` | 4.0 problem report. Inbound `status`, `delivery`, `problem-report`, unknown names: Debug line, no reply. The reply thread check (512) and the reply-build fault boundary are shared with the 3.0 handler (moved, not changed).
- **DC-4. No session → no reply, nothing read.** A 4.0 `delivery-request` without a return-route session for this (peer, local) pair returns `null` before the coordinator is called. Reason: L52/L69 require `return_route: all` on every request; the library endpoints never send a reply without a session (FR-RR-04), so this is not visible on our transports; and an empty `delivery` there would say "nothing available" while messages may be queued, if a hand-built host sent it out of band. (3.0 keeps its `status`, which the endpoints also drop.)
- **DC-5. `MessagePickupOptions.EnableV4`, default `true`,** read from the registration probe like `CoordinateMediationOptions.EnableV2`; both pickup handler factories run a build-time consistency check (registered ⇔ enabled in the settings in effect) and throw `InvalidOperationException` naming the property, never a value. No `EnableV3`: CM offers no "newest only" switch either, and 3.0 is what the field speaks (Identus); a host that wants 4.0 only can register `MessagePickup40Handler` by hand over a `MessagePickupQueue` (public constructor), which the DI tests cover.
- **DC-6. `MessagePickupVersion { Negotiate = 0, V4 = 1, V3 = 2 }`** and `MediatorClientOptions.MessagePickupVersion` (default `Negotiate`), the shape of `CoordinateMediationVersion`. Negotiation generalises `FeatureNegotiation`: the same bounded reader and role rule (owner decision O-1, #99), a second query pair (`https://didcomm.org/message-pickup/4.*` then `https://didcomm.org/messagepickup/3.*`), 4 wins over 3, neither → `MediationNotSupportedException` (docs only change). `NegotiatedVersionCache` becomes generic over the version enum; the channel keeps one cache per protocol. Each `PickupClient` call resolves the version after the route (pin, else cache, else one query on the same route); a live stream resolves it once before it starts and keeps it. The negotiation log template differs from Coordinate Mediation's (the live wallet counts that one).
- **DC-7. Per-version client wire `PickupWire`** (internal, like `CoordinateMediationWire`): requests and their exchange specs per version, status/delivery readers, "is a delivery of this version", "does the mediator answer an acknowledgement". 4.0 readers are strict where the text is: a `delivery` without `attachments` (L259), or with more attachments than `message_count_limit` (L255, refused from the count before any is read, L-055), is a `MediationProtocolException`; a `status` is not an expected answer to a 4.0 `delivery-request`. `MediatorAnswerTypes` gains `status (4.0)`, `delivery (4.0)` (Delivery kind) and `problem-report (4.0)` (ProblemReport kind).
- **DC-8. One-way send** `IMediatorExchange.SendOneWayAsync(route, request, name, mediatorDid, localDid, ct)` for the 4.0 `messages-received`: `SendOptions.ReturnRoute = null` (no header, no answer read), bounded by `RequestTimeout` plus the shutdown token, counted against `MaxPendingRequests`; timeout → `TimeoutException` naming the request id. Used by `FetchAsync`'s ack, `AckAsync` (then the existing `status-request`, sharing the last chunk's `RequestTimeout`), and the live stream's flush/end. The live stream's scheduling is not touched (owner decision on #96's live stream, 2026-11-14, #88 comment 6887124928: "If it finds more in the live stream, the next step is to propose simplifying how the stream schedules its work, not a seventh patch.").
- **DC-9. Existing 3.0 test harnesses pin `V3`** so the 3.0 suites keep testing 3.0; new suites cover negotiation and 4.0.
- **DC-10. Live harness.** With negotiation on, R-2 (our wallet against our mediator) speaks 4.0 by itself: that is the "our client against our mediator over 4.0" cell, so no new cell. R-2's drained-fetch check becomes version-aware, it asserts the negotiated pickup version, and gets a sabotaged twin (expects 3.0). The Identus cells negotiate 3.0 (Identus 1.2.1 discloses `https://didcomm.org/messagepickup/3.0`, roles `["mediator"]`, `DiscoverFeaturesExecuter.scala#L43-L47` at `b85da0b`) and are otherwise unchanged; M-8 now also sends the Discover Features query over the WebSocket (confirmed by the live run).

### Owner decisions taken during this run (2026-11-20; posted on #88, comment 7052968916)

The question (raised by us, relayed by the coordinator): routing.md L57 only asks a sender to encrypt what it forwards ("This content should be encrypted for the next recipient."), while pickup allows only encrypted attachments (3.0 L172 "The ONLY valid type of attachment for this message is a DIDComm v2 Message in encrypted form."; 4.0 L261 "The ONLY valid type of attachment for this message is a DIDComm v1 or v2 Message in encrypted form."). Our mediator stored and delivered a non-encrypted message (on main, 3.0 too).

- **OD-1 (owner decision, option 1 as put): "The mailbox refuses any message that isn't encrypted, whoever supplies it (a sender's forward or the host's own code), stores nothing, and reports a new 'not encrypted' result. The sender already got its 202, as with every mailbox refusal today."**
  - How we build it (ours): the check is in `PickupCoordinator.DeliverAsync` (behind `MessagePickupQueue.DeliverAsync`, the one door into the mailbox: the forward sink in pass-through and rewrap mode, a host's own calls, and the live push, which stores first). Order: after the size bound (L-055: the parse is bounded by `MaxAdmissiblePayloadBytes`), before the registration lookup and before anything is leased or stored. Outcome `PickupDeliveryOutcome.NotEncrypted` (new, appended); the forward sink records it as a drop with its own forward-outcome name and a rate-limited line (id only).
  - **"Encrypted form", defined from the spec (ours):** the outermost layer is a JWE — an anoncrypt or an authcrypt envelope (v2.1 message_structure.md L65 "A **DIDComm encrypted message** is an encrypted [JWM]…", L71 "…the [`typ` property] of the JWE"; RFC 7516 §7.2.1 makes `ciphertext` REQUIRED in the JSON serializations). The structural check, without decrypting: the bytes are valid UTF-8 throughout (checked first, since the JSON reader does not validate strings and member names; added after ADV2-1) and parse as one JSON object under the library's strict reader (`DidCommJson.StrictDocument`: no duplicate member names, no trailing content) and Core's `EnvelopeDetector` classifies that object as `Encrypted` — the same rule the library's unpack uses to decide a message is a JWE (FR-API-03), so the mailbox and every unpacker agree (L-041). A plaintext message (no `ciphertext`), a signed-only message (a JWS: `payload` + `signatures`/`signature`, no `ciphertext`) and anything that is not a JSON object are refused. Whether the JWE decrypts is the recipient's business (the mediator holds no key for it). In rewrap mode what is stored is the mediator's own forward to the recipient, a JWE, so it passes whatever the sender's inner message was; the recipient's client then opens the inner message (documented).
- **OD-2 (owner decision: "OK, as described"):** "if a delivery carries a message that isn't encrypted, the wallet client reports it as a failed item and doesn't acknowledge it, the same treatment as any attachment it can't decode. The host can discard it, and otherwise it ages out of the mailbox." How we build it (ours): F-2 above, the same structural rule as OD-1, judged on the attachment's outermost form before any unpack.
- **OD-5 (owner decision 2026-11-21, from PR #143 review round 1, "Counts as pushed: wait"; #88 comment 7066089431):** "One simple rule: only a connection's explicit 'not sent', or no attempt at all, keeps a message eligible for a live push. Safe with any connection type a host writes. Matches the reviewer's expected result. Cost: the PRD's retry rule narrows, failed or timed-out pushes are delivered at the next collection, and 3 older tests change their expectations."
  - The question (raised by us while fixing review P2-1, relayed by the coordinator): with the returned-push mark set at take, does a send that was attempted and then threw (a deadline, a fault, a cancellation) count as definitely not sent? Our two session types throw only before anything reaches the wire, but a host's session type might not. PRD FR-PICK-09 "Retries" said such a push is tried again at the next wake-up.
  - Applied: FR-PICK-09 "Retries" narrowed (a push the session did not take, `NotSent`/`TooLarge`, or never attempted, is tried again; one attempted and then faulted or timed out stays marked and goes to pickup); the architecture doc's "Retries" and the OD-3 subsection; the CHANGELOG; the three #95 tests listed in the round-1 record below.
  - Kept apart from it: ADV4-1's "a push in hand when its session closes counts as returned" was OUR implementation choice, now replaced by the invariant (marked from the take, cleared only on a definite not-sent); a push a closing session answered `NotSent` stays eligible, as OD-3 is worded ("pushed live and returned unconfirmed").
- **OD-6 (owner decision 2026-11-21, from PR #143 review round 2, "Stop promising a status"; option 1 as put by us, relayed by the coordinator):** "AckAsync returns the mediator's own status when it sends one (3.0's optional answer), and nothing (null) otherwise: always under 4.0, and for a 3.0 mediator like Identus that skips it. Nothing is ever made up, so it can't be stale. Removes the extra requests. Cost: the return type becomes nullable (unpublished package only); the cookbook, sample 11 and a live-interop check adapt; callers who want the queue state call GetStatusAsync."
  - The spec lines it rests on (checked by the coordinator and by us): Message Pickup 3.0 L193, "The `mediator` **SHOULD** send an updated `status` message reflecting the changes to the queue."; 4.0 L294 is the same paragraph without that sentence; 4.0 L35, "Removed return route all from `messages-received` messages, as it is not required."
  - The question (ours, after the round-2 repro): round 1's opening `status-request` did not order the status after the acknowledgement when the connection dropped mid-call, and nothing in 4.0 confirms an acknowledgement. Making the promise hold would need plumbing the protocol does not offer, so the claim is removed instead.
  - Built (ours): `Task<PickupStatus?>`; no `status-request` from `AckAsync` in either version; 3.0 returns the last chunk's own answer or `null`; a failure is an exception, never `null`; the channel waits for a 3.0 status over a WebSocket half of `RequestTimeout` once the message is sent and never past its `RequestTimeout` (`ExchangeAllowingNoAnswerAsync`'s `answerWait`).
- **OD-7 (owner decision 2026-11-21, "Also: client waits for the close"; reviewer's option 2):** "Change the released WebSocket transport so shutting down waits a bounded time for the mediator to answer the close, which it does only after handling earlier messages. Reverses a deliberate design that refuses to wait on hostile peers, in a published package."
  - The question (L-073, as put by the coordinator on 2026-11-21): three choices, "Docs and samples only", "Also: server finishes a received message" ("Closes most of the gap for every app, but it is a behaviour change in a published package, and doesn't help when the connection resets before the server reads the bytes"), and "Also: client waits for the close". The owner picked the third. The owner answered "same round".
  - Built (ours): in the WebSocket loop behind the registry-aware `MapDidCommWebSocket` and `MapDidCommMediator`, a message whose last frame is in is handled under a token of its own; from the connection's end it gets `WebSocketReturnRouteSession.DefaultCloseGrace` (5 s, the server's existing allowance for an ending connection) or the host's `ApplicationStopping`, whichever first; reads keep the connection token (at most one finish per connection); the session closes at the drop; a connection that already ended opens no session. - **OD-4 (owner decision 2026-11-21, "Document it as a known limit"; #88 comment 7063319275):** "No code change. The docs say a mediator must accept at least 10 ids per confirmation for the live stream to confirm on time; otherwise delivery waits for the next collection.   - The question (QA-2's O-1, put by us, relayed by the coordinator): the wallet's live stream confirms up to 10 messages per `messages-received`; a mediator configured to accept fewer (ours with `MessagePickupOptions.MaxAckIds` below 10, allowed when `MaxDeliveryBatch` is below 10) refuses it, silently under 4.0, and the messages come back at the stream's next collection.
  - Where it is stated (ours): the XML docs of `MessagePickupOptions.MaxAckIds` and `MaxDeliveryBatch`, `PickupClient.ReceiveLiveAsync`'s acknowledgement remarks, the architecture doc's client "Documented limits", the CHANGELOG. - **OD-3 (owner decision, option 2 as put: "Never push it live again"; #88 comment 7055549619):** "A message pushed live and returned unconfirmed waits until the recipient asks for it. Same rule for 3.0 and 4.0, since one mailbox serves both. Cost: the mailbox marks such a message (a small addition to the unpublished store contract), plus tests. A recipient that only listens live and never asks would not get it until it does."
  - The question (raised by QA-2 as QA2-Q1, put by us, relayed by the coordinator): a live push left unacknowledged went back to the queue at its lease's end and was pushed live again at the grant's next wake-up (the #95 design, 3.0 and 4.0). Spec lines (didcomm.org@a26926c): 4.0 L302 "_Live Mode_ is the practice of delivering newly arriving messages directly to a connected `recipient`."; L304 "Messages already in the queue are not affected by _Live Mode_; they **MUST** still be requested with `delivery-request` messages."; L308 "If a message is not acknowledged, the message **MUST** be added to the queue for later pickup."; 3.0 L203 = L304 with a lowercase "must".
  - How we build it (ours, engineer R, `6f0f242`): `MessageLease.LivePush` (init-only) on every lease the coordinator creates for a live push, never on a `delivery-request`'s; the store marks a record (`QueuedMessage.LivePushReturned`, init-only, store-set) when a live-push lease ends unacknowledged by `ReleaseLeasesAsync(owner)` or by running out (judged lazily, written when the lease is replaced or the owner's leases are released), never by `ReleaseAsync` (a push the session did not take) or `PassOverAsync`; a live-push lease request never takes a marked record; a `delivery-request` takes it as before; counts, quotas and `status` unchanged. A push the session took while it closed is ended by an owner release (so it is marked) instead of a give-back by id: before, the two raced (L-057). `TakeNextAsync` refuses a marked record a store hands to a live push (outside the contract; released, not pushed, still picked up). Known edge: a push abandoned at its deadline whose send stays unresolved past `LeaseTimeout` can be marked by a `delivery-request` in that window; nothing is lost, it stays pickup-only.
