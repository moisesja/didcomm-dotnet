## Threat model (L-031)

- **Who talks to it.** Anyone who can reach the endpoint; only an authcrypt sender is a peer (`MediatorPeer.TryGet` over `ReturnRouteEligibility.TryGetPeer`, the rule that opens a session, L-041), never the plaintext `from`. Unauthenticated shapes are dropped before the type or body is read: nothing applied, no reply, one rate-limited line with the id. Senders of forwards reach the queue through #95's sink without authentication. Host code calls `MessagePickupQueue` and implements `IMessageStore`.
- **What a peer can do.** Count, lease, acknowledge and toggle live mode under its own authenticated DID only: every store operation is keyed by the peer's DID, and a message id means something only under that key, so another grant's ids are plain misses (never reported, never echoed, same work). Pinning its own queue under leases, or publishing a DID document so large that its envelopes exceed the budget, harms only itself.
- **`recipient_did`.** Authorised by one `FindGrantByRecipientDidAsync` lookup + `grant.PeerDid == peer`. "Not registered" and "registered under another grant" make the same store call (one `FindGrantByRecipientDidAsync`) and, with "not a bare DID" (never looked up — bareness is a property of the asker's own input), get the same answer (`status` echoing the value with `message_count: 0`) without the message store being read: no registration oracle here, a smaller surface than #93's accepted `client_error`. Over 2048 characters is malformed before anything parses it (FR-API-09).
- **Registration at delivery time (owner decision).** A filtered request is authorised before the store is touched. In an unfiltered batch every distinct recipient DID of the leased records is checked again; the leased records of a DID that no longer authorises the peer are not delivered and are removed by id (they would otherwise block the head of the queue; JC-22). If the check cannot be made, the leases are released and nothing is delivered or removed (L-054). Leftovers of a revoked grant are not delivered while the peer holds no grant (empty `status`) — and are again if the same peer is granted mediation again, since records are kept under the peer's DID; removing them is the host's `PurgeGrantAsync`.
- **Floods.** A sender can fill one recipient's queue to the per-grant budget and no further; all grants together are bounded by the store-wide budget (open enrolment can exhaust it with self-made grants — a stated availability limit, like W-2). Queued, leased, live-unacknowledged and not-yet-due payloads all count; nothing is ever copied on release. Enqueue outcomes never reach the forward's sender (#95 answers 202 first).
- **Work per message, each bound applied before the work (L-055).** `limit` is clamped and the byte budget applied inside the lease call; `message_id_list` is refused from its length before any entry is read; a payload over the admissible size is refused before any lookup; one mediation-store read per request plus at most `MaxDeliveryBatch` for the delivery-time check.
- **Faults (L-054).** Mediation store, message store (each method), id generator, session registry `Find`, session send and logger each fail closed on every path that reads them: no reply, nothing half-applied, leases taken are released. When the dispatch token is cancelled only `OperationCanceledException` leaves. What a store returns is copied and validated inside the boundary (a leased record must carry the caller's grant key).
- **Logs and errors.** Message id through `LogId` (128-character cap), exception type names, enum names, counts. No DID, `recipient_did`, attachment id or thread id at any level. `MalformedMessageException` text names the member and the rule only.

## Judgement calls (architect design reconciled with mine; each has a reason)

- JC-1. **Outcomes are enums, not `QueueFullException`** (the issue's draft). A full queue is an expected state any sender can cause; with enums a throw means "store fault" and nothing else (#93's `RecipientStoreOutcome` precedent).
- JC-2. **The byte budget is verified by the session, on the bytes it hands to the transport.** The handler holds plaintext; `SessionOutbound` packs. Options weighed: a trial pack in the handler (double encryption, two key resolutions, duplicated pack options, no cover for a pipeline push), an analytic size (couples to the JWE serialisation), a cached per-pair overhead (wrong exactly when a DID document changes). Chosen: `IReturnRouteSession.TrySendAsync(message, maxPackedBytes, ct)` → `Sent | NotSent | TooLarge`. The batch is chosen by arithmetic (`PickupSizing`), the `delivery` is pushed through the bounded send, and on `TooLarge` the last attachment's lease is released and the message re-sent until it fits (the PRD's trim-and-repack). The handler returns `null` after pushing a `delivery`: over HTTP the pushed message is the 200 body.
- JC-3. **Sizing.** Constants: envelope allowance 32 KiB (protected header, `recipients[]`, iv, tag; measured ≈ 1.1 KiB for one X25519 key), `delivery` skeleton allowance 8 KiB (three DIDs at 2048 + a 512-character thread id + fixed text), 96 bytes per attachment (descriptor + a 64-character id + rounding). `BatchPayloadBudget` = ¾ × (largest plaintext whose base64url ciphertext fits − skeleton − batch × 96), every division rounded down; 564 525 bytes (≈ 551 KiB) at the 1 MiB default (measured by QA: a single payload of that size packs to 1 021 967 bytes with 2048-character DIDs, a 512-character thread id and a 64-character id). The same number is the admission bound (`MaxAdmissiblePayloadBytes` = min(`MaxReceiveBytes`, budget)) and the per-lease byte budget, so an admitted payload always fits alone whatever `limit` is. PRD said "≈ 576 KiB"; the row now gives the computed number. A budget below 1 fails `Validate()` / construction.
- JC-4. **Store key = `(grantPeerDid, id)`; `recipient_did` is a filter inside the grant.** The issue's `PeekAsync(recipientDid, …)` / `AckAsync(recipientDid, ids)` carry no grant key and "peek" that mutates is misnamed → `LeaseAsync` / `AcknowledgeAsync(grantPeerDid, ids)`.
- JC-5. **A lease is state on the stored record** (lease id + owner token + expiry instant). It ends by acknowledgement, release (by ids — naming the lease id, so only the taker gives a record back — or by owner) or lazily by timeout; no timers, nothing re-inserted, position kept. The owner token is an opaque string minted per live session (never on the wire); HTTP leases have none. (The lease id came out of the QA pass: an unconditional release by ids let a late clean-up end a lease a later request had taken.)
- JC-6. **A live push is one store step**: `EnqueueAsync(message, lease)` inserts the record already leased to the target session, so no `delivery-request` can take it in between.
- JC-7. **`status` counts** records that are due and unexpired, leased ones included (FR-PICK-04: the count drops on acknowledgement). Not-yet-due records are retained and count against the budget but are not reported until due (a client looping on the count would otherwise spin). Members emitted: `message_count`, `total_bytes`, `live_delivery` always; `recipient_did` when the request had one; the three time members when the count is above zero.
- JC-8. **Thread ids (DD-11).** `status`, `delivery` and the problem report's `pthid` use the request's `thid` if present, else its `id`; a live `delivery` has no `thid`. Putting `thid` on a 3.0 `status` is an addition (the page shows none; 4.0 requires it; harmless and what #96 correlates on). A request thread id over 512 characters is malformed (bounds the echo; the replay guard's `MaxMessageIdLength` default).
- JC-9. **No session.** A `delivery-request` dispatched without a return-route session leases nothing and is answered `status` (the library endpoints log such a reply and do not send it; nothing could carry the batch and a lease would only lock the queue). `messages-received` is still applied. A session bound to another (peer, local) pair is treated as absent.
- JC-10. **Problem report only for `live_delivery: true`** on a connection that cannot do live delivery (HTTP, or no session) — the spec's wording; `false` there is answered `status{live_delivery: false}`.
- JC-11. **Attachment data is base64url without padding** on emit (DIDComm v2.1 attachments; what `ForwardProcessor` reads) and decoded leniently on receive (padding and the standard alphabet accepted). `TryParseDelivery` checks structure and decodes; it does not inspect the payload (the mediator relays bytes; per-attachment unpack failures are #96's).
- JC-12. **Ids** are minted by the coordinator through `IMessageIdGenerator` (default UUID v4), must be unreserved characters and at most 64 long, else the delivery is `Faulted`; the store reports `DuplicateId`. Wire ids (`message_id_list`, attachment ids on parse) are capped at 2048 (FR-API-09).
- JC-13. **Several live sessions for one peer**: one target, the newest session with the flag on. A lease has one owner; pushing to every session would duplicate.
- JC-14. **A not-yet-due payload is never pushed live**; it is queued and picked up once due.
- JC-15. **Store faults → no reply** (the #93 precedent; pickup has no error shape for them).
- JC-16. **Acknowledgement needs no grant lookup**: it is confined to the caller's own key. **Toggling live mode needs no grant**: it is per-session state bounded by the session registry, and pushes only ever follow a grant.
- JC-17. **`AddMessagePickup()` is order-independent** with respect to `AddCoordinateMediation()`; a missing `IMediationStore` fails when the queue is first built, with a message naming the fix.
- JC-18. **Lease selection is a FIFO prefix**: it stops at the first eligible record that would pass the byte budget (never skips to a smaller one), except that the first eligible record is always returned, so a record admitted under an older, larger budget still reaches the bounded send instead of blocking silently.
- JC-19. **A payload this peer's envelope can never carry** (its own DID document inflates `recipients[]` past the allowance, so even a single-attachment `delivery` is over the budget once packed) is neither delivered nor removed: it is **passed over** — a mark the store keeps on the record (`IMessageStore.PassOverAsync`), for a period that starts at `LeaseTimeout` and doubles each time — and the same request looks further (JC-21) and delivers what is queued behind it. Five versions (the fifth came out of the PR #107 review, see the end of this file): (1) released at once — the QA pass showed over the real endpoints that the record is then offered first for ever and nothing behind it is ever delivered, and any sender can cause that for a many-key recipient; (2) removed — two QA agents independently showed that the verdict depends on the request's own framing (a 512-character thread id and a 2048-character filter are part of what is measured), so the same message was delivered or destroyed depending on which request met it first, and a late verdict could remove a message another request had delivered meanwhile; (3) kept under the lease, the request answered `status` — three agents (QA-3, QA-5, the resource red team) showed that a recipient polling no faster than the lease then never gets what is behind it; (4) this one: kept under the lease and the request goes on. It loses nothing and needs no new store operation. Cost: such a message stays stored and counted until it expires or is purged (a client must not loop on the count alone), and costs up to a batch of packs once per lease period.
- JC-21. **A request looks further when a batch comes to nothing** (its head was passed over, or all of it was unregistered leftovers): it leases again and tries what is queued behind, so `status` in answer to a `delivery-request` means "nothing deliverable now", as the spec has it. Work per request is bounded whatever the queue holds: at most 2 × `MaxDeliveryBatch` lease rounds and 2 × `MaxDeliveryBatch` sends (a send is a full pack). A store that hands back a record the request has already set aside is outside its contract (no reply, leases released).
- JC-22. **The delivery-time registration check removes exactly the records it looked at**, by id, not every record of the DID (first version: `PurgeRecipientAsync`). Both red-team agents showed the gap between the check and a purge-by-DID: a message accepted for the DID after it was registered again was deleted undelivered (L-039). A registry answer that names no usable peer is a fault of the check, not "gone" (L-054). The role no longer calls `PurgeRecipientAsync`; it stays for hosts.
- JC-20. **Expired records never keep a new message out, store-wide**: when the in-memory store's own bound would refuse, every grant's expired records are swept once and the bound judged again (QA pass; before, only the arriving grant's were).

## Review

## PR #107 — review round 1 (reviewer comment of 2026-11-12T21:42Z against `4af9383`)

The reviewer's own notes are in `tasks/todo20261112-pr107-review.md` (theirs; not edited). Both findings were checked against the code and reproduced before anything was changed; both are real.

- [x] R1-1 **[P2] Delivery could starve for ever behind messages that do not fit.** JC-19 version 4 remembered "this record did not fit alone" only as the request's lease. That memory expires with the lease (and, over a WebSocket, ends with the connection), while the per-request budgets of JC-21 start again with every request. With more such records than one request can try (two, at `MaxDeliveryBatch` 1) and a recipient that asks only at or beyond `LeaseTimeout`, every request spent its whole budget on the same records and answered `status`: the reviewer's reproduction, which I re-ran (five polls, 2/4/6/8/10 sends, nothing delivered). I had seen the shape — the QA and red-team passes drove three rewrites of this rule — and stopped one step short: I bounded the work per request without asking what carries progress from one request to the next.
  Root cause: progress state kept in something that expires (a lease) or belongs to someone who leaves (a connection). Fix: the memory is the record's own. `IMessageStore.PassOverAsync(grantPeerDid, messageIds, leaseId, until)` ends the caller's lease on the record (compare by lease id, like `ReleaseAsync`) and keeps it out of `LeaseAsync` until `until`; the record counts how often (`QueuedMessage.PassOvers`). The coordinator passes a record over until `now + LeaseTimeout × 2^PassOvers` (saturating). Only time ends the mark — not lease expiry, a give-back, or a session close. The work bound per request is unchanged; nothing is dropped. Because the periods double, they outgrow any polling interval: after a bounded number of requests all such records are set aside at once and the request reaches what is deliverable.
  - Tests (`MessagePickupForwardProgressTests`, 20 cases; all fail with the fix reverted): the reviewer's exact case (delivered by the third poll); a theory over batch sizes 1/2/3/10, 3–25 blockers (well beyond the 2 × batch budget) and polls 60 s, 61 s, 5 min, 15 min, 1 h and 1 day apart, each request checked against its send and round bound; a recipient that reconnects for every request with the clock standing still; the doubling itself and that closing the connection or giving leases back does not end the mark; a pass-over that fails (no reply, leases given back, nothing removed); saturation. `MessagePickupStorePassOverTests` (6): the store contract of the new operation. Over the real endpoints: the slow poller and the reconnect (`MessagePickupHttpTests`, `MessagePickupWebSocketTests`).
- [x] R1-2 **[P2] Clean-up after a closed session was unbounded.** `PickupSessionState.OnClosed` queued one independent `ReleaseLeasesAsync(…, CancellationToken.None)` per tracked session, and a session is tracked as soon as it toggles live mode — before any grant lookup. Against a store whose call does not complete, 1 000 connect–toggle–disconnect cycles of a peer without a grant left 1 000 calls in flight (reproduced). The session registry bounds simultaneous sessions, not what closed ones leave behind.
  Fix, three parts: (1) a session that never took a lease queues nothing (`MarkLeasing` is set before the store call that records a lease under the session's token; the close reads it after marking itself closed, and every taker re-checks the closed mark afterwards, so neither side can miss the other); (2) one worker makes the release calls, one at a time, in close order; (3) the backlog — waiting plus in flight — is at most `PickupSessionTracker.MaxPendingReleases` (1 024) owner tokens; a close that finds it full is not queued (counted in `DroppedReleases`, rate-limited log line) and its leases end by `LeaseTimeout`. Closing still never waits for the store, and the release still runs without the closing thread's execution context.
  - Tests (`MessagePickupCleanupBoundTests`, 4; all fail with the fix reverted): the reviewer's reproduction through the real dispatcher (1 000 connections, no grant, a gated store: zero release calls); 1 100 connections that each leave a lease behind against a gated store (never more than one call in flight, never more than 1 024 pending, 76 dropped and logged, close non-blocking; after the gate opens the backlog drains one at a time in order, the drained sessions' messages are deliverable at once and the dropped ones' after the lease timeout); a release that throws does not stop the worker; a backlog that was full takes closes again.
