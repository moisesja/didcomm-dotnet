## Design calls (architect review applied; each has a reason)

- **DC-1. Codec stays internal.** Add the mediator direction to `CoordinateMediation20` (`MediateRequestUri`, `KeylistUpdateUri`, `KeylistQueryUri`; `TryParseMediateRequest`, `TryParseKeylistUpdate(message, maxUpdates, out …)` = `RequireUpdatesWithin` then bounded `ReadUpdates`, `TryParseKeylistQuery`; `CreateGrant(from, to, string routingDid, thid)`, `CreateDeny`, `CreateKeylistUpdateResponse`, `CreateKeylist`) plus `MediationBodies.WriteRoutingDid(string)`. Reason: no new IVT grant, no `DidComm.Mediator.Client` API to demonstrate, no pattern set for #100's codec. Not an owner stop: nothing becomes public.
- **DC-2. Public `CoordinateMediation20Handler`** (not the issue text's `CoordinateMediation2Handler`), sealed, `IProtocolHandler, IProtocolHandlerRoles`, same constructor shape as `CoordinateMediationHandler`. Reason: FF.2 (b) hand-built hosts need it to serve 2.0 wallets; the name matches the public `MediatorServiceProtocols.CoordinateMediation20` and the codec. It sets the naming pattern for #100 (`MessagePickup40Handler`), noted for the owner.
- **DC-3. A 2.0 grant carries `routingDids[0]` of what `MediationCoordinator.RequestAsync` returns:** for a repeat request that is the stored grant's first DID, not today's configuration (FR-MED-05: re-issued unchanged). Chosen inside the reply's fault boundary, so a host store that returns a grant with no routing DID is "not answered (ArgumentException)", never thrown. The `keylist` always carries `pagination`, as 3.0's `recipient` does.
- **DC-4. One `MediationCoordinator` per handler.** Reason: sharing needs an internal singleton and internal constructor overloads on both public handlers; separate log categories tell an operator which version a peer speaks; the counters only bound log volume (Interlocked, so at most twice the lines: first and every 1000th per version). Stated in the coordinator remarks.
- **DC-5. `CoordinateMediationOptions.EnableV2`** (default `true`), read from the registration probe like `UseAsForwardRecipientRegistry`: a call that leaves it true registers the 2.0 factory (TryAdd) and `AddProtocol<CoordinateMediation20Handler>()`. No removal of earlier registrations. Instead, **both handlers' factories check, when first built, that the setting in effect (`IOptions`) agrees with what was registered**, in both directions, and throw `InvalidOperationException` naming the property (never a DID): this catches `Configure<CoordinateMediationOptions>`, appsettings binding and mixed repeated calls, which the probe cannot see. Under `AddMediator()` it fires at start-up (the hosted service resolves the dispatcher). Reason (architect proposed "false on any call wins" by removing descriptors): removal would depend on the internal shape of `AddProtocol<T>()`'s descriptor in another package; failing loudly costs nothing and matches the existing "set it on every call" rule of `UseAsForwardRecipientRegistry`. `Validate()` unchanged. `AddMediator()` docs only (`Projecting(cm:)` already reaches the probe).
- **DC-6. No client code change for #99 itself.** The issue's `MediationClientOptions.PreferredVersion` is #96's `MediatorClientOptions.CoordinateMediationVersion` (#96 notes override issue bodies); negotiation already prefers 3.0 and falls back to 2.0. The two negotiation changes in O-1 wait for the owner.
- **DC-7. Interop vectors are inline templates** in a test class citing the commits above (the real implementations have no checked-in 2.0 JSON fixtures except scala-did's parser suite, whose `keylist` vector is reused).
